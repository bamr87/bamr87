# The Jobs page carries a job's state, ages and why it may be slow — evidence

> **Feature:** `HUB-064` (FR60, bamr87/bamr87#556) · **Scenario:** `verify/scenarios/console-job-status.yml` · **Result:** **PASS** (2/2 viewports) · **Generated by:** `node verify/runner.mjs --only console-job-status --base http://127.0.0.1:4121` against the public build (`CONSOLE_BASE=/ tools/console/build-pages.sh` into a scratch directory, served statically) on 2026-11-16, plus a hand-driven pass on a worktree console (below).

Each time the console reads a job it derives a `state` (`queued`, `running`, `stalled`, `done`, `failed`), the seconds since it was sent (`age_s`) and since its log last grew (`idle_s`), and the reasons it may be slow (`queue_wait`, `collector_lag`, `long_step`, `no_heartbeat`): `GET /api/jobs/{id}/status`, every `GET /api/jobs` row, the MCP's `job_status` and `jobs_list(state=…)`, and the Jobs page ([tools/console/docs/job-status.md](../../../tools/console/docs/job-status.md)).

## The public build (the scenario)

The published page has no console, so its Jobs list is empty without a GitHub token. Every step passed at both viewports: the route answered 200, the table rendered, the Stalled tile and its line `running, log quiet past its threshold` were there, the `age` and `idle` column headers were visible, and the page did not scroll sideways.

## A running console (the interactive pass)

Driven with Playwright MCP against this branch's console on `127.0.0.1:4113`: `tools/console/app.py` served by uvicorn from the worktree, with `CONSOLE_AUTO_HEALTH=0` and its own `DASH_CONSOLE_JOBS` in scratch. A small driver (scratch, not committed) registered four demo operations in the console's `OPS` table, so every state came from a real subprocess through the real `JobManager` instead of a fixture:

- `demo-step`: ticks once a second. Three runs of 3 s succeeded first, then a 1,200-tick run became the long step.
- `demo-quiet`: prints one line, then sleeps, so its log stops growing.
- `demo-fail`: exits 3.
- `demo-write`: `remote: true`, so one holds the GitHub-write lock and a second waits behind it.

A stand-in collector rewrote a scratch `sessions.json` (the driver pointed `live.SESSIONS` at it) every 5 s for 200 s and then stopped, as a dead collector does. No allowlisted operation ran, nothing touched GitHub, and every demo job was cancelled at the end.

The MCP layer against the same console (`tools/console/mcp_layer/server.py`, the `.venv-mcp` interpreter, `Console(url="http://127.0.0.1:4113")`), with the long `detail` sentences cut here:

```json
job_status(job_id="05f0d75cfea4") →
{"id": "05f0d75cfea4", "op": "demo-quiet", "status": "running", "state": "stalled",
 "age_s": 380.6, "idle_s": 380.6, "stall_s": 120,
 "diagnostics": [{"code": "no_heartbeat", "detail": "no log output for 381 s (stalled past 120 s)"},
                 {"code": "collector_lag", "detail": "the live collector last wrote .dash-live/sessions.json 190 s ago …"}]}
jobs_list(state="stalled") → count 1: 05f0d75cfea4 demo-quiet stalled
job_status(job_id="ffffffffffff") → tool error: console GET /api/jobs/ffffffffffff/status -> 404: no such job
```
