# A site build opens on the bashOS desktop: an icon for every repo, the site's own app first, and the profile and the console one click away — evidence

> **Feature:** `HUB-NEW:console-site-builds` · **Scenario:** `verify/sites/site-front-door.yml` · **Result:** **PASS** (2/2 viewports, 42 steps each) · **Generated by:** `node verify/runner.mjs --scenarios verify/sites --base http://127.0.0.1:4150` against the bash-365 site build (`CONSOLE_SITE=bash-365 SITE_URL=http://127.0.0.1:4150 OUT=<scratch> tools/console/build-pages.sh`, served statically with `python3 -m http.server`), 2026-11-20

In a site build whose settings say `front_door: desktop`, `/` is the bashOS desktop under that site's title and mark. The dock holds an icon for every repo in the registry, in groups: the site's pinned apps, the framed frontends, the repos that open as the generated repo app, then Fleet, Profile and Console. Nothing is fetched from another origin until an app is opened. The pinned app opens the live site in a frame the page's own policy admits; a repo with no frontend opens as the repo app; the profile that `/` used to be answers at `/home`, in a window or as a page of the classic console, whose header carries the site's name and leads back to the desktop. The palette opens from the menu bar. At a phone's width the same icons are a home screen. Nothing scrolls sideways.

Measured by the scenario's own checks, at both viewports:

- **Identity is the site's.** The tab title is `bash-365 — BASH Consulting`, the tab icon and the menu-bar mark are `bash-365-mark.svg`, and each is compared with `snapshot/site.json`, not with a literal.
- **An icon for every repo.** 44 icons: the registry's 41 repos (compared name by name with `snapshot/apps.json`), then Fleet, Profile and Console; the first is the pinned `bash-365.com`.
- **Nothing asked until opened.** Zero requests to another origin and zero frames while only the desktop is on screen.
- **The frame policy.** The page's `frame-src` names `https://www.bash-365.com` and holds no wildcard; the frame's `src` is the registry's live address, and its sandbox has no top-navigation.

## The interactive pass

The same build in the Claude desktop app's browser pane (Chromium), by hand, at 1440×900 and 375×812: the desktop opened at `/`; `bash-365.com`, `kvlite` and Profile were opened from their icons and tiled with the taskbar's button, four windows side by side with the live BASH site running in one; at phone width the home screen showed all 44 icons with no sideways scroll and the BASH site opened full-screen. No console errors were recorded in either pass.

## Can the live site be framed?

Yes. Read on 2026-11-20 with `curl -sIL`: `https://www.bash-365.com/` and `/services/` answer 200 from Azure Static Web Apps with `strict-transport-security`, `referrer-policy: same-origin` and `x-content-type-options: nosniff`, and with neither `X-Frame-Options` nor a `Content-Security-Policy`; the HTML carries no policy `<meta>`; `staticwebapp.config.json` in bash-365/bash-365.com sets no `globalHeaders`. Nothing in that repository blocks a frame, so no change is owed there. The apex `https://bash-365.com/` is a GitHub Pages redirect page and is a separate registry entry (`bash-365-apex`).

## The default build is unchanged

Checked on 2026-11-20 by building the default site twice, from `origin/main` (17cc5b24) and from this branch, both with `tools/console/build-pages.sh` and no `CONSOLE_SITE`, and comparing the two trees: the same 464 files outside the hashed `assets/`, all 352 HTML pages identical once the bundle's content hash is masked, the policy `<meta>` (`frame-src 'self'`) included, and all 102 snapshot documents identical apart from build timestamps and the name of the branch each was built on. The one addition is `bash-365-mark.svg`, which Vite copies from `web/public/` into every build and nothing in the default build references. Every scenario in `verify/scenarios/` was then run against the branch's default build served at the root: 28 of 29 passed. The one that did not, `desktop-context-menu`, lost one step at its 1024-wide viewport (`focus_returned`: "Execution context was destroyed, most likely because of a navigation") and passed on both reruns; the same step failed one of two runs against a build of `origin/main`, so it is a timing fault of that scenario and not of this change.
