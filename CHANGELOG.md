# Changelog

This changelog tracks the hub's **versioned public interface**: the reusable workflows member repos call by reference, and the checker they run. The interface, the tag scheme (`vX.Y.Z` plus a floating `vX`) and the meaning of each bump are defined in [`docs/WORKFLOW-VERSIONING.md`](docs/WORKFLOW-VERSIONING.md). Changes to the dash, the site, registries and generated data are not listed here.

The format follows [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/), and versions follow [Semantic Versioning 2.0.0](https://semver.org/spec/v2.0.0.html). Keep exactly one `## [Unreleased]` heading.

## [Unreleased]

### Added

- `tools/conformance.py`: `--instance DIR` (default `$FLEET_HOME`, else `--hub`) on `check`, `fleet` and `kinds`. `--hub` stays the framework checkout the spec, contracts, kits and tools are read from; the instance is the control plane whose `_data/projects.yml` lists the repos and whose `projects/` holds them, so one checkout of the framework can grade another owner's fleet. `standards.yml` and the issue-type labels are the instance's when it has them, else the framework's. `fleet --write` with no path writes the instance's `_data/conformance.yml`. With no instance named nothing changes (ADR 0011, phase P0).
- `pr-review.yml`: merge readiness (ADR 0012), off unless the calling repo's `vars.PR_READINESS_ENABLED` is `true`. With it on, the one PR comment also lists what is left before the pull request merges (checks, base, draft state, the review gate and its label, the governance trace, the task list, review threads), stays while anything is left, and gives way to one `COMMENT` review per head commit when nothing is. In the hub the workflow also runs on the pull-request events that start no workflow (`pull_request_target`: opened, reopened, marked ready, converted to a draft, pushed to, labelled, unlabelled, edited); a stub gains that trigger with kit 0.3.0. The reusable workflow's inputs, jobs' permissions and behaviour with the variable unset are unchanged, and its sparse checkout of the hub now includes `tools/` and `_data/`.
- Proposed constitution § 31 / amendment `mission-and-about-section`: a fleet-wide mission-statement standard (constitution § 1 is one direction statement plus exactly three numbered missions, adopted by a numbered amendment, with matching README and AGENTS.md one-liners) and a repository about section that functions as a public site map, documented in [docs/ABOUT-SECTION.md](../docs/ABOUT-SECTION.md) and [docs/FLEET.md](../docs/FLEET.md).
- Proposed amendment `pr-queue-maintainer-actions` (#863): whether a merge or close the maintainer confirms in the Harness Console PR queue is his own action. Three options for Amr to choose from (allow both, close only, keep disabled); nothing is enabled, and the `pr_queue.merge.enabled` / `pr_queue.close.enabled` switches from #864 stay `false`.
- `pr-review.yml`: the findings channel (constitution § 19.3). A repo check uploads a `fleet-findings` artifact of JSON lines (`path`, `line`, `rule`, `severity`, `message`, `kind`) instead of commenting itself, and the reusable posts each finding on a line the PR adds as one inline comment with its severity, a hidden `(path, line, rule)` key so a later push never reposts it, and the § 19.4 signature. `content` and `docs` findings are dropped on Dependabot and release-please PRs (§ 19.6), a malformed artifact posts nothing and still leaves the CI-failure sticky, at most 20 new comments post per review (and posting stops after GitHub refuses 5 in a row), the sticky counts findings by severity while something fails, and the job summary lists every finding and what happened to it. The caller's permissions are unchanged (`actions: read`, `pull-requests: write`); fleet stubs get it with the next `v2` minor cut. Contract: `templates/pr-review/README.md`.
- `release-please.yml`: the release is made by a GitHub App. When the caller holds `RELEASE_APP_CLIENT_ID` and `RELEASE_APP_PRIVATE_KEY`, each job mints an installation token for its own repo (contents and pull-requests write, revoked when the job ends) and uses it to tag, to open the release PR and to push the lockfile commit, so the PR runs CI and the tag fires the workflows that listen for it. Nothing expires and one app serves every owner it is installed on. Both secrets are declared under `workflow_call.secrets`, so a caller under another owner can pass them by name. Setup: `docs/RELEASES.md` "The release app".

### Changed

- `claude-run` (and so `ai-lane.yml`): a transient API failure (529, 503, 502, `overloaded`) is retried inside the run, on the same credential and only when the failed call's payload shows that nothing was billed (zero cost, zero tokens, at most one turn). It used to fail the step on the first one. Two optional step environment variables tune it: `AI_TRANSIENT_RETRIES` (default `2`, at most `5`, `0` turns it off) and `AI_TRANSIENT_BACKOFF` (default `30 90` seconds). A call that billed anything is never re-run, and the budget, turn-cap, auth and quota paths are unchanged (`ai-runner` kit 0.4.1).
- `release-please.yml`: the credential order is the release app, then `RELEASE_PLEASE_TOKEN`, then `GITHUB_TOKEN`. A caller that holds only the PAT releases exactly as before. The key arms the app: a key without the client ID, or an app that cannot mint a token (not installed on the repo, a key that is not the app's), fails the run and says which, and neither falls back to the PAT. The client ID alone is inert.

### Deprecated

- `release-please.yml`: the `RELEASE_PLEASE_TOKEN` secret. It is still read where the release app is not provisioned, and goes when the fleet's callers no longer hold it.

### Fixed

- `tools/conformance.py` 0.3.3: UPS-BE-10 (/healthz, /readyz) and UPS-BE-11 (/version) apply their `app (server-rendered)` qualifier from specs/BACKEND.md. An `app` repo with no server side (a browser-only SPA, a game, firmware, a mobile client) now passes both as N/A instead of failing two MUST rows it cannot meet. Kind `api`, a `manage.py`, `config.ru`, `Dockerfile`, `Procfile` or wrangler config, a server framework dependency (Django, FastAPI, Flask, Express, Next, Hono and others) or code that serves HTTP itself (a `BaseHTTPRequestHandler` subclass, an asyncio or wsgiref server, Go's net/http) keeps them checked as before. No spec row changed.
- `claude-run`: after the install, the step always prints `claude-run: Claude Code <version> on Node <version>`, and warns, naming `$RUNNER_TEMP/npm-install.log`, when an install that exited 0 left no `claude` on PATH, so an install that "succeeded" with the wrong release is visible in the run log (#499).
- The fleet-doctor's priority fallback no longer queues a healthy, high-volume workflow. An unflagged workflow now needs its wasted job-minutes, less the minutes its own `cancel-in-progress` superseded, to clear `remediation.min_cost_waste_min` and the new `remediation.fallback_max_waste_pct` share (default 5 %) of its job-minutes. This frees the doctor slots that went to `markdown-oneline` (#920), `drift-check` (#831) and githubai/bashcrawl CI (#886).
- `templates/pr-review/` 0.2.0: the seeded stub declares a workflow-level `concurrency` group, `pr-review-caller-<head sha>` with `cancel-in-progress: false`, so a repo whose own tests require a concurrency group on every workflow accepts it (githubai's `test_every_workflow_has_concurrency` failed on the 0.1.0 stub). - `tools/check-drift.sh` check (d) now runs `tools/docs_index.py --lint`, so a documentation lint failure fails the drift gate instead of passing unseen (#503). The PRD's FR45 points at HUB-048, the eval baseline it describes, instead of HUB-049 (#500).
- Three `_data/fleet.yml` model fields named ids outside `ai_models.allowed`: the verify agent's `sonnet` alias and JEV conflict tiers 1 and 2 (`claude-haiku-4-5-20251001`, `claude-sonnet-5`). They are now `claude-sonnet-5-5`, `claude-haiku-5-5` and `claude-sonnet-5-5`, and `test_ai_budget.py` fails any Claude `model:` in `fleet.yml` that is not an exact allowed id (#540).

## [2.2.0] - 2026-11-16

Minor release: the floating `v2` moves to it. It brings the tag level with `main` on Claude authentication. `v2.1.0` was cut before the OAuth-only change of 2026-11-15 (#859) landed, so a caller pinned to `@v2` still ran the earlier `claude-auth`, `claude-run`, `ai-lane.yml` and `fleet-verify.yml`, which read `ANTHROPIC_API_KEY` and follow the caller's `CLAUDE_AUTH_ORDER`, while a caller on `@main` ran the OAuth-only ones. With this release both refs behave the same: those four use `CLAUDE_CODE_OAUTH_TOKEN` alone, name `api_key` in an order only to report that it is ignored, and keep their key inputs declared and unread so that no caller breaks. A caller with no OAuth token skips its agent step as before; none turns red. It also carries the `ai-runner` kit 0.4.0 pins (lanes and the runner called at `@v2`, d58f335c) and the entries below. The four files ride along on the tags and are not yet under the compatibility promise ([`docs/WORKFLOW-VERSIONING.md`](docs/WORKFLOW-VERSIONING.md)); this is the release that makes pinning them to `@v2` safe, which bamr87/bamr87#458 (UPS-WORK-10, UPS-QA-40) needs before it moves the fleet's callers off `@main`.

### Fixed

- `templates/prose/` 0.5.0: the seeded `markdown-oneline.yml` checks out a pull request's head by SHA instead of by branch name, and its repair step skips the push when the head branch is already gone. An auto-merged bot PR (Dependabot, JEV numbering) has its branch deleted before the job starts, so the checkout by name failed after ~35s of retries and left a red X on a PR that had already merged. Same two hunks as the hub's own copy (bamr87/bamr87#846). `archive/` gains the outgoing 0.4.0 shape and the 0.3.0 shape (a leading blank line), which a 2026-09-13 template edit stranded without archiving: `tools/fanout.sh --kit prose --upgrade` now reaches the 11 untouched copies that carry the bug (10 on 0.3.0, 1 on 0.4.0). Three hand-edited copies (README, it-journey, gitorio) need the change by hand. `templates/prose/test_prose_kit.py` holds the template and the archive to this.
- A cancelled check run that a later run of the same check passed no longer counts as a failure. A workflow that cancels in progress on every `labeled` event, such as verify kit 0.1.0 callers and zer0-mistakes' evidence gate, leaves one cancelled row per label burst in a commit's check rollup, and GitHub's own rollup state calls the commit FAILURE. On 2026-11-15, 25 fleet pull requests read red this way; the real run had passed. `tools/check_rollup.py` holds one rule for it: a CANCELLED check run is set aside when a later run of the same check (same workflow name, same check name) on the same commit exists, and that later run is judged as it stands. A lone cancellation, a failure followed by a pass, and a pass followed by a failure all stay red. The weekly close-out's live gate (`tools/weekly/closeout.py` `checks_green`), the decision index (`tools/console/decision_index.py`: failing, Dependabot and ready-to-merge) and the PM review (`tools/pm_review.py`: `pr_ci_red` and the Fleet project's CI field) read checks through it. The last two now read the rollup's contexts as well as its state. They correct only a red they can prove was a superseded cancellation, and keep GitHub's state when the contexts run past one page.
- `templates/pr-review/` 0.2.0: the seeded stub declares a workflow-level `concurrency` group, `pr-review-caller-<head sha>` with `cancel-in-progress: false`, so a repo whose own tests require a concurrency group on every workflow accepts it (githubai's `test_every_workflow_has_concurrency` failed on the 0.1.0 stub). The key matches the reusable `pr-review.yml`'s group, but the name differs, because GitHub cancels a run whose caller and called workflow hold the same group. `archive/` keeps the 0.1.0 stub, so `tools/fanout.sh --kit pr-review --upgrade` moves untouched copies.
- `templates/release-pipeline/` 0.2.0: the `release.yml` that `tools/adopt-release.sh` seeds calls `bamr87/.github`'s `release-please.yml` and `publish.yml` at `@v1` instead of `@main`, which UPS-WORK-10 and UPS-QA-40 reject (bamr87/bashos#97 failed on it). `bamr87/.github`'s `v1` tag holds both files byte-identical to `main`, with the same inputs, secrets and outputs, so a seeded repo releases exactly as before. The kit is now versioned: a `VERSION`, a `# kit: release-pipeline vX.Y.Z` stamp in the seed, and `archive/release-0.1.0.yml`, the shape it replaces. `tools/adopt-release.sh <repo> --upgrade` rewrites a repo's `release.yml` only when it is byte-identical to the current template or an archived shape, and reports a hand-edited copy without touching it.

## [2.1.0] - 2026-11-14

Every change to the versioned interface since 2.0.0 is additive or relaxes a failure, so this is a minor release and the floating `v2` moves to it. `standard-ci.yml` gains three optional inputs whose empty defaults keep the old behaviour; `release-please.yml` gains `strict-pr-creation` (default `false`) and now warns, instead of failing, on the one PR-creation denial a caller cannot fix (#406), and its internal `release-please-action` moves from v4 to v5, whose only breaking change is the Node 24 runtime GitHub-hosted runners provide; `spec-gate.yml` and `pr-review.yml` are new, so `@v2` callers of either stop failing to resolve. Files that ride on the tag without the compatibility promise move too: `claude-run@v2` gains the explicit `@latest` CLI install that Node 20 runners need and the empty-model fix, and `fleet-verify.yml` fails an app that is configured but does not start.

Same tests, same advisory coverage table; the console, pages and spec files ran 2.2 to 2.5 times slower under the old tracer, and the change is measured at about 40% less test time on the named shards, the hub's largest single use of Actions minutes.
- `templates/verify/` 0.2.0: the seeded `verify.yml` caller of `fleet-verify.yml` stops re-running a verdict it already has. A label other than `verify` now gets a concurrency group of its own and a skipped job, so it neither re-runs the pass nor cancels the run in flight (Dependabot's two labels started 3 runs per PR, the content agents' four started 5). The `push:` trigger is gone: 151 of 155 sampled pushes to a default branch were merges of a PR that had just been verified, and a dispatch still verifies the default branch. Every PR commit and the `verify` label run as before, and `gate` is unchanged. Over 14 days these runs were 469 of the fleet's 1,009 Verify runs and 946 of its 2,840 wall-clock minutes. `archive/` keeps the 0.1.0 shapes, so `tools/fanout.sh --kit verify --upgrade` moves the 23 untouched copies.

Claude Code now declares `engines: node>=22`, so on the fleet's Node 20 a bare package name made npm fall back to 2.1.197, which current models reject (`400 … version 2.1.280 or newer is required`); every `claude-run` step on Node 20 failed over to the API path. The CLI is a native binary and runs on any Node.

- `tools/jev` loop runner (HUB-060): the per-run sandbox evidence works on Claude Code 2.1.308 — the sandbox runtime's per-command line is read from its stderr under `SRT_DEBUG` (which the agent environment now sets) and recorded by `ai-run` in the outcome file, the `--settings` read-fence line is required as well, and the live canary's judge no longer reads a traceback's echoed source as a network success, pairs each `cat` with a python twin, and plants neutrally named fixture files (bamr87/bamr87#560, decision 4c).

Before this a headless attempt inherited the operator's own rules, every edit was denied, and it reported `success` with the conflict untouched.

## [2.0.0] - 2026-10-14

`standard-ci.yml` stops ignoring failed dependency installs, which can turn a green caller red, so this is a major release. Callers pin `@v2`; `v1` keeps the lenient installs.

### Changed

- **Breaking:** `standard-ci.yml` fails the job when a dependency install fails, instead of masking it with `|| true` (#310). The project itself is installed only when it is installable (a `setup.py`, or a `pyproject.toml` with a `[project]`, `[build-system]` or `[tool.poetry]` table): editable first, then a regular install, and a failure of both fails the job. A `pyproject.toml` that holds only tool config is skipped with a notice.

### Added

- `standard-ci.yml`: docs-only skip. A new `changes` job (5-minute timeout) lists the files changed by the push or pull request; when every one matches `docs-paths`, the `ci` job is skipped (a skipped job satisfies a required check). New optional inputs: `skip-docs-only` (default `true`), `docs-paths` (default `**/*.md **/*.markdown docs/** LICENSE* .github/ISSUE_TEMPLATE/** .github/*.md`) and `timeout-minutes` (default `30`, the previous hard-coded value). The check fails open: an unknown base, a compare error or a 300+ file diff runs CI as before. (#354; part of the Actions waste reduction, Oct 14, #268, #348).
- `site-quality.yml`: a reusable site quality scan (Lighthouse CI, axe-core at 390 px and 1366 px, pa11y contrast) with `mode: build` (build the Jekyll site against a fresh theme resolved to a commit SHA, recorded in the job summary and report) and `mode: url` (scan live URLs). New interface, additive: inputs `mode`, `config`, `base-url`, `source`, `build-command`, `build-command-token` (default `false`: a custom build gets no token unless the caller opts in), `theme-cache` (default `false`), `expired-allowlist-level`, `gate`, `artifact-name`, `retention-days`, `hub-ref`, `node-version` (default 22), `ruby-version`; outputs `status`, `errors`, `warnings`, `theme-repo`, `theme-sha`, `report-artifact`. Every threshold comes from the caller's config (`templates/site-quality/site-quality.schema.json`, `schema: site-quality/v1`); the defaults only report, and a collector that crashes while its check is gated fails the run. Runtime pinned exactly in `.github/site-quality/` with a committed lockfile, installed with `npm ci --ignore-scripts` and kept current by a Dependabot npm entry (axe-core and @lhci/cli minor/major bumps excluded: those are reviewed and released by hand). `lighthouse.public_upload` is honoured only in public repos; private and internal repos keep Lighthouse reports in the run artifact. UPS-QA-40, UPS-QA-41 and UPS-REPO-07 carry the hub-only exception for this runtime, declared in `specs/QUALITY.contract.yml` and parsed by `tools/sanctioned_lockfiles.py`.
- The `site-quality` kit (`templates/site-quality/`, `tools/fanout.sh --kit site-quality`): a caller pinned `@v1`, a report-only config template, the JSON Schema, pass/fail fixture sites, and draft rows UPS-QA-60..63 (`rollout: warn`, contract `specs/QUALITY.contract.yml`).

## [1.0.0] - 2026-10-03

The first tagged baseline: the interface exactly as it stood on `main` when the tags were introduced, so existing `@main` callers can move to `@v1` with no behaviour change.
