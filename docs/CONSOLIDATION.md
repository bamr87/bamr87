# Fleet consolidation — fewer repos, one place per concern

> Decision record for the 2026-10-19 consolidation: which repositories merge into which, how the merge is done, what the hub does on each side, and the decisions still open. Status lines here are updated as the pull requests land.

## Why

Forty-plus submodules had grown several pairs and clusters that share one purpose — a tool and its experiment, a site and its sidecar, three takes on git tooling. Each extra repository costs a CI run, a credential, a harness, a kit fan-out and a registry row, and the dash reports on all of it. Merging the clusters makes the fleet smaller without losing anything: every merge imports the source's **full history** under a subdirectory, so `git log` and `git blame` keep working at the new path.

## The recipe

The same one [zer0-CMS documents](https://github.com/bamr87/zer0-CMS/blob/main/docs/MONOREPO.md): clone the source, drop its tags, rewrite it with `git filter-repo --to-subdirectory-filter <path>` (bare `#123` references become `owner/repo#123` so they still point at the source's issues), then `git merge --allow-unrelated-histories` into the target on a branch, and open a pull request. Nested `.github/workflows/` never run from a subdirectory: the thin callers a target already runs at the root (standard CI, the `@claude` handler, the prose gate) are dropped from the import; bespoke workflows stay as the reference for porting. Nothing is archived or deleted by the merge itself.

## The squash merges dropped the imported history

Every merge PR above was **squash**-merged (and so were zer0-CMS #29 and #36), so each target's `main` carries the imported tree as one commit: `git log`/`git blame` under `lawmode/`, `packages/gitnexus/`, `retro-pi/` or any zer0-CMS import path stop at the squash. The rewritten histories are intact in each PR's `refs/pull/<n>/head` and in the originals — and `bamr87/1987` has since been deleted, so its PR ref is the last copy. The repair is zer0-CMS's `tools/history/graft.sh`: a branch that lifts the paths out, merges the rewritten histories back and replays the later commits, ending on a tree identical to `main`, landed as a **fast-forward** (a merge commit keeps the history reachable but blame still stops at the squash). zer0-CMS#39 does it for zer0-CMS; law-ai, gitorio and rewind-arcade need the same before any of their originals is archived. Merge an import with a merge commit or a fast-forward — never a squash.

## Decided since (zer0 stack)

zer0-CMS [ADR 0002](https://github.com/bamr87/zer0-CMS/blob/main/docs/adr/0002-one-home-cutover.md) settles open decision 1 for the zer0 family: zer0-CMS is the only home; every original is archived except `bamr87/zer0-mistakes`, which becomes a read-only mirror because `remote_theme` only loads from a repository root; releases are cut in zer0-CMS with component-prefixed tags; every site publishes from one Pages deploy on `zer0-mistakes.com` under its own sub-path (`sites/2005` is built by `year-of-ai.github.io`); and content goes DB-first in Wagtail one site at a time. Its cutover milestones C0–C7 end with the hub retiring the eight remaining zer0 submodules. `bamr87/1987` was deleted on GitHub; `sites/1987/` in zer0-CMS is its only home.

**The theme returns (2026-10-21):** zer0-CMS [ADR 0005](https://github.com/bamr87/zer0-CMS/pull/52) reverses ADR 0002 for the theme alone. `bamr87/zer0-mistakes` never stopped being the real home (v1.31.3, the gem, zer0-mistakes.com and the consumer propagation all run from it, ten commits since the import, the mirror workflow never armed), so the monorepo's unique theme changes went back upstream as [zer0-mistakes#559](https://github.com/bamr87/zer0-mistakes/pull/559), `packages/zer0-mistakes/` leaves zer0-CMS in [#52](https://github.com/bamr87/zer0-CMS/pull/52), and **zer0 studio** — a Rails workbench that designs, customizes and updates the theme from a browser, every write a digest-guarded atomic rename, every script the theme's own — lands beside it at `studio/` in [zer0-mistakes#560](https://github.com/bamr87/zer0-mistakes/pull/560). zer0-CMS stays the content-management half and builds each site with the theme that site declares (gem or `remote_theme`, pinned per site). This hub change re-adds the theme as the submodule `projects/zer0-mistakes` and lets `update-submodules.yml` track it again; the registry row loses its mirror note and `scout: false`.

## Open decisions

1. **The rest of the zer0 family.** zer0-CMS's MONOREPO.md is explicit that `zer0-mistakes` (the `remote_theme` source every Pages consumer names, plus the gem release), `zer0-image-generator` (gem release), `zer0-pages`, `drsai`, `barodybroject` and the demo sites still do something only their own repository can do today. Their hub submodules stay until, per repository, either the monorepo becomes the place work happens and the original is a read-only mirror fed by `git subtree split`, or the original stays authoritative. One direction per repository, never both.
2. **The lineage organizations.** year-of-ai carries thirteen year repos and ai-world-view four country repos, all generated knowledge bases. Only the two org root sites were added; the per-year and per-country repos are tracked through the content atlas. Registering all seventeen as submodules would undo the point of this exercise — say so if you want them anyway.
3. **cv-pro's deploy.** bamr87/cv is archived (2026-10-19), so the live CV site stays at its last build until cv-pro publishes it; cv-pro carries those workflows under `cv/.github/workflows/` as reference. Port the publish and release workflows to the root, repoint the `sync-cv` skill at `cv-pro/cv/data/cv.json`, then archive both originals.
4. **Archiving — done 2026-10-19.** Archived (read-only, still readable, Pages sites frozen at their last build): bamr87/zer0-image-generator, books, drsai, zer0-pages, zer0-pages-remote, zer0-demo-cookbook, zer0-demo-garden, barodybroject, year-of-ai/2005, lawmode, gitnexus, git-with-the-program, retro-pi, cv and cv-builder-pro. Their open pull requests (zer0-image-generator #31, gitnexus #2–#7, cv-builder-pro #91–#95) were closed with a pointer to the new home first; the branches stay readable. **bamr87/zer0-mistakes is deliberately not archived** — it becomes the mirror (zer0-CMS ADR 0002). Consequences until the replacements are armed: the gem and PyPI releases, the Azure deploy and the CV site no longer update — zer0-CMS C2 (releases), C4 (Pages) and cv-pro's publish workflows take them over.
