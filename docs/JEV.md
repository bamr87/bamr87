# JEV — the agent logic engine

> The fleet's harness-level AI agent logic engine: conflict-free numbering (ids assigned at merge, never in a pull request), tiered pull-request conflict triage and resolution, and loop step specs that CI and a local run render alike.

JEV is the planned agent logic layer of the fleet's harness — it is the "JEV" row of the Roadmap (2027 Q1) in [`bamr87/it-journey`](https://github.com/bamr87/it-journey)'s `PRD.md`, whose text is generated by that repo's `scripts/prd-machine/prd-machine.py`. **That PRD is not edited here.** Marking the row as *in progress: first capability = conflict triage, `bamr87/bamr87` `tools/jev`* is a fan-out follow-up against the prd-machine's own input, in it-journey's own pull request ([amendment 0002](amendments/0002-conflict-free-numbering.md), fan-out step 7).

This page is the operator doc for what exists today, in `tools/jev/`. Design rationale and the rules it is held to: [amendment 0002](amendments/0002-conflict-free-numbering.md). Module reference: [`tools/jev/README.md`](../tools/jev/README.md).

## Why

A pull request that conflicts costs a human a context switch, and the fleet produces them faster than a human clears them: four scheduled agent loops, a three-tier issue pipeline, seven fan-outs and a person all open pull requests against the same `main`. Two things follow from looking at what those conflicts actually are.

**Most of them should never have existed.** They are two branches claiming the same sequential id — `HUB-033`, `FR28`, amendment `0002`, the same `## [Unreleased]` line — or a generated file whose content nobody is supposed to decide by hand. Neither is a disagreement. Both are an artefact of letting a pull request pick a number from a stale read of `main`.

**The rest are not all the same size.** A two-line conflict in one source file and a forty-file conflict across a migration and a workflow are different problems, and spending the same thing on both is how an AI budget disappears.

So JEV has two halves: remove the spurious conflicts at the source, and resolve what is left at the cheapest tier that can actually finish.

## Half one — assign at merge

A pull request never picks a number. It writes a **fragment**:

| New thing | File | Placeholder |
| --- | --- | --- |
| Feature | [`features/features.d/<slug>.yml`](../features/features.d/README.md) | `id: HUB-NEW` |
| Requirement | the same fragment's `prd_new:` | `kind: FR` + a slug `key:` |
| Changelog entry | [`changelog.d/<slug>.md`](../changelog.d/README.md) | — (no number to pick) |
| Amendment | [`docs/amendments/proposed/<slug>.md`](amendments/proposed/README.md) | `**Number:** NEW` |

Fragments reference each other by slug — `HUB-NEW:<slug>`, `FR-NEW:<key>`, `NFR-NEW:<key>`, `AMEND-NEW:<slug>` — so a feature can name the requirement it serves before either has a number.

When the pull request lands, [`jev-number.yml`](../.github/workflows/jev-number.yml) runs on `main` under `concurrency: jev-number`, which is what makes the assignment safe: two pushes a second apart compile one after the other instead of both reading "the next free id is 033". `tools/jev/number.py` then

1. reads the highest id ever used in each series — the catalog, the PRD, the changelog and every amendment record, so an id that was published and later removed is still spent;
2. assigns the next free one to each fragment, in sorted filename order, so the same tree always produces the same numbers;
3. compiles the fragments into `features/features.yml`, the PRD's requirement list, `CHANGELOG.md`'s `[Unreleased]` section and `docs/amendments/NNNN-<slug>.md`, and appends the amendment's index row;
4. rewrites every slug reference to its number, and **reports** (never silently drops) one it cannot resolve;
5. deletes the fragment — the entry now lives in the compiled file and nowhere else;
6. regenerates the PRD feature block, the docs index and `CATALOG.md` (and the other generated spans — see [Main-only generated files](#main-only-generated-files); it runs after every push to `main`, not only fragment pushes);
7. publishes through [`publish-data`](../.github/actions/utilities/publish-data/action.yml), which pushes if branch protection allows it and opens a pull request if it does not. No `--admin`, no bare push to a protected branch.

```bash
python3 -m tools.jev number next     # what the next free id is in each series
python3 -m tools.jev number plan     # what the pending fragments would be assigned
python3 -m tools.jev number apply    # assign, compile, consume (what CI runs on main)
python3 -m tools.jev number lint --base origin/main
```

**Generated files are not merged, they are regenerated.** [`.gitattributes`](../.gitattributes) marks each one `merge=jev-regen`; the driver ([`tools/jev/merge-regen.sh`](../tools/jev/merge-regen.sh)) keeps *ours* and records the path in `.git/jev-regen-pending`. Git cannot install a merge driver from `.gitattributes`, so each clone opts in once:

```bash
git config merge.jev-regen.name   "keep ours, regenerate"
git config merge.jev-regen.driver "tools/jev/merge-regen.sh %O %A %B %P"
```

Two files are marked `merge=union` instead, because they are genuinely append-only and order-free: `docs/amendments/README.md` (the index table) and `_data/jev_resolutions.yml` (the ledger's record list). Union takes **both** sides and does not deduplicate, so it is correct only where a repeated or reordered line is harmless. It is not safe on a file with front matter, a header block, or a list that is read positionally — do not extend that list without checking.

### Main-only generated files

**The merge driver is not enough on GitHub.** GitHub's mergeability check ignores custom merge drivers, so `merge=jev-regen` never stops two pull requests from being reported `This branch has conflicts` on the same generated file — and a PR-side drift check made every branch commit a fresh copy of exactly that file. The choice (option **b** of the two considered):

| Option | Verdict |
| --- | --- |
| (a) gitignore the files and build them in CI or Pages | Rejected: `CATALOG.md` and `docs/README.md` are read on GitHub and linked from `README.md`, `AGENTS.md`, `SCHEMA.md` and the site; removing them breaks those links |
| (b) keep them committed; only main's post-merge job writes them; PR CI fails an edit | **Chosen** — no link, check or test changes meaning |

What that means in practice:

- **Main-only files** — `CATALOG.md` (`tools/gen-catalog.py`) and `docs/README.md` (`tools/docs_index.py`) — carry `jev-main-only` in [`.gitattributes`](../.gitattributes). [`jev-number.yml`](../.github/workflows/jev-number.yml) regenerates them after **every** push to `main` (`python3 -m tools.jev generated regen`) and publishes `chore(jev): assign ids and compile pending fragments`; with nothing to change it publishes nothing. A pull request that edits one fails `drift-check.yml` (`python3 -m tools.jev generated guard`) with the fix: `git checkout origin/main -- <file>`, and edit the generator's *source* instead. The post-merge publish branch (`chore/jev-*`) is exempt.
- **Generated spans in hand-written files** — the PRD feature block, README `AUTO:projects` and the `docs/DASH.md` dash CLI reference — are regenerated by the same job. A pull request may still edit the rest of those files; with `JEV_SPANS_ADVISORY=1` (set in `drift-check.yml`, and by the conflict engine's validation) `check-drift.sh` (b) and `governance_lint.py check` report a stale span as a warning, not a failure.
- **Not main-only:** `projects/SCHEMA.md`, `_data/specs.yml`, `_data/features_index.yml`, `_data/cv_portfolio.json`, `_data/deep_dive.json`. Their own loops (fleet-pulse, deep-dive) or the registry flow write them through their own publish branches, and `check-drift.sh` (h) still gates `projects/SCHEMA.md`; making them main-only would fail those loops' PRs.
- The conflict engine takes **main's** copy of a main-only file on a conflict and neither regenerates nor `--check`s it on a branch; the merge driver does the same locally.

This refines a constitution §2 invariant, so it ships with a proposed amendment record (`docs/amendments/proposed/generated-files-main-only.md`, numbered at merge).

**Transition.** Everything already numbered keeps its number: `HUB-001`–`HUB-032`, `FR1`–`FR27`, `NFR1`–`NFR10`, amendment `0001`. `governance_lint.py` and `features_index.py` still read the compiled files, the fragment directories are additive, and `number lint` reports on every pull request but only **gates** once `_data/fleet.yml` `jev.numbering.enforce` is `true` — a one-line change to make after amendment 0002 is ratified.

## Half two — the conflict engine

```bash
python3 -m tools.jev conflicts scan                     # the fleet's CONFLICTING open PRs
python3 -m tools.jev conflicts triage  --pr owner/repo#123
python3 -m tools.jev conflicts resolve --pr owner/repo#123 --dry-run
python3 -m tools.jev conflicts budget  --scheduled
```

**Detect.** Open pull requests whose `mergeable` is `CONFLICTING` — across the hub, every registry repo (`_data/projects.yml`) and the `jev.orgs` list (`year-of-ai`, `ai-world-view`, `bash-365`, `EissaLab`, `zer0-mistakes`). `UNKNOWN` is deliberately excluded: GitHub computes mergeability lazily, so an unknown is a question GitHub has not answered, not a conflict. Triggered by [`jev-conflicts.yml`](../.github/workflows/jev-conflicts.yml) every six hours (`23 */6 * * *`), on a push to `main`, on `repository_dispatch: jev-conflicts`, and by hand.

**Triage.** A throwaway clone, the base merged into the head, and the wreckage read: which files conflicted, how many hunks, how many lines between the markers, and what kind of file each one is. The kind comes from the repo's own `.gitattributes` first (`git check-attr`) and from `jev.generated_paths` / `fragment_paths` / `union_paths` otherwise. [`tools/jev/classify.py`](../tools/jev/classify.py) then returns exactly one tier and the reason, deterministically — the same pull request always triages the same way, and the reason prints without a transcript.

| Tier | Cost | Entry condition | Resolution |
| --- | --- | --- | --- |
| **0** | $0, no model | Every conflicted file is generated, a fragment, union-safe, or an id collision | take ours + re-run the generators · union both sides · `number.py apply` to renumber |
| **1** | ≤ $0.25/attempt · Haiku 4.5 · 8 turns | ≤ 3 files **and** ≤ 40 conflicted lines, and nothing under `.github/workflows/`, no auth/secret file, no migration, no lockfile | capped headless `claude -p` on the conflicted tree |
| **2** | ≤ $1.50/attempt · Sonnet · 24 turns | ≤ 15 files **or** ≤ 400 conflicted lines, or tier 1 failed | the same, stronger model |
| **3** | $0 | anything larger; a binary or a lockfile; a semantic conflict in a workflow or a secret; a squash-only repository; two failed attempts; the monthly cap reached | label `jev:needs-human` and comment the triage report |

The blocking rules are evaluated **first and unconditionally**, so a one-line conflict in `Gemfile.lock` is a human's, not the cheapest work on the board.

**Resolve and prove it.** Every tier merges the base into the head with a **merge commit** — never a rebase, never a force-push, because the pull request's history belongs to whoever opened it and a force-push detaches review comments from their commits. Then it validates: a sweep for leftover conflict markers, `git diff --check` on the tree and the index, no unmerged paths, and whichever of the repository's own gates it carries (`tools/check-drift.sh`, `schema_lint.py`, `governance_lint.py`, `docs_index.py --check`, `run-all-tests.sh`). A failed validation is **discarded** — `git merge --abort`, back to the clean trial merge — and the next tier starts over. Nothing half-resolved is ever pushed.

**What it will not do.** Never merges a pull request. Never force-pushes or rebases. Never uses `--admin`. Never touches settings, secrets or branch protection. Only same-repo branches (a fork's branch is tier 3 by construction) and only authors in `jev.allowed_authors`. A `jev:needs-human`, `agent:hold` or `human-review` label keeps the pull request. `common.assert_no_admin`, which every `gh` call JEV makes itself goes through (`common.gh`), is an allowlist: only the `gh <noun> <verb>` commands JEV issues pass (label create, pr comment, edit, list or view, issue create, list or view, repo clone, list or view, variable get, and `api`), named by the argv's first two words, so `gh pr merge`, an issue close, a secret or variable write or delete (the `remove` alias included), a `repo sync`, a flag before the verb (`gh pr -R o/r merge`, which gh would still run) and any command nobody listed are refused, as are any `--admin`, a comment's `--edit-last` or `--delete-last`, and every `gh api` call but a GET or an inline GraphQL query (no mutation, no `--input` or `@file` body; a shorthand bundle such as `-iXPUT` is read as gh's parser reads it, and one the guard does not know is refused); what `gh repo clone` hands git after `--` is held to the `git clone` options below. `common.assert_safe_git` is an allowlist too: the subcommand must be one JEV runs (no alias, autocorrected typo, `send-pack` or `http-push`), a global option one it passes (no `--config-env` or `--exec-path`), a `-c` key one it sets (no `alias.*`, `help.autocorrect`, `remote.*` or `push.*`, and no `core.hooksPath`, `core.fsmonitor` or `core.pager`, which the wrapper pins and a later `-c` would undo), and the call's `env` may set only the `GIT_*` names JEV hands git (`GIT_LFS_SKIP_SMUDGE`, `GIT_TERMINAL_PROMPT`, `GIT_CONFIG_NOSYSTEM`, `GIT_OPTIONAL_LOCKS`, the author and committer identity, and `GIT_CONFIG_GLOBAL` or `GIT_CONFIG_SYSTEM` only as `/dev/null`: no `GIT_DIR`, `GIT_COMMON_DIR`, `GIT_TEMPLATE_DIR`, `GIT_SSH_COMMAND` or any other) and may move `HOME` or `XDG_CONFIG_HOME`, where git finds its global config, only when that config is `/dev/null`. The calls that could plant config a later push follows are held to the options JEV uses: `clone` (its `-c` only the pinned hardening settings, no `--mirror`, `--template` or `--upload-pack`), `init` (`-q`, `-b`, `--bare`; no `--template`, whose `config` file is copied into the new repository), `fetch`, `remote` (list and remove only) and a `git config` write (only the keys `workspace.harden` and the commit identity set, the hook and fsmonitor keys pinned to `/dev/null` and `false`; no `include.*`, `url.*` or `--file`). A push is refused for a force, mirror, delete or prune flag in any spelling (bundled short flags, long-option prefixes), an option JEV does not pass, and any refspec but an explicit `<src>:<dst>`, so a push refspec or mirror flag in config never applies (git ignores the first and refuses the second beside a refspec), and `common.git` names the pack program on every push and fetch (`--receive-pack=git-receive-pack`, `--upload-pack=git-upload-pack`), so a `receivepack` or `uploadpack` in config, a program git runs on a push or fetch to a local or ssh remote, never runs either. Both are covered by `tools/test_jev_conflicts.py`. The loop runner's planner and filer are `tools/dash-gen` subprocesses whose own GitHub reads and writes do not pass these guards; what bounds them is the spec-declared argv, its pinned subcommands and the § 13.6 gate on `--apply`.

## Cost model

| Where | What it caps |
| --- | --- |
| `_data/fleet.yml` `budget.jev.tier1_usd` / `tier2_usd` | one attempt, passed to the CLI as `--max-budget-usd` |
| `budget.jev.monthly_usd` | **$10/month** for the whole engine, inside the fleet's monthly ceiling (`harnesses.budget.monthly_ai_usd`, $200) |
| `budget.jev.scheduled_stop_pct` | a **scheduled** run stops at 80% of the month, so a human's manual run still has budget on the 28th |
| `jev.max_attempts` | two failed resolutions on one pull request, then a human |
| `budget.loops.monthly_usd` / `scheduled_stop_pct` | **$25/month** for every [local loop run](#the-loop-runner-p1) together, a `--scheduled` run stopping at 80%; each attempt is still capped by its step's `budget.call_sites` entry. Every cap and ceiling must be a finite number above 0 (YAML's `.inf` is refused), and a ledger figure that is not a finite number of 0 or more is charged at its row's cap, or stops the run when the cap is unreadable too. `budget.loops` + `budget.jev` stay inside `harnesses.budget.monthly_ai_usd` (`test_ai_budget.py`) |

JEV is not a `budget.call_sites` entry, and that is deliberate: those are keyed `<workflow file>:<job id>` and `test_ai_budget.py` holds each against a literal `--max-budget-usd` in that job, which only works for a workflow **step** that runs one agent. JEV runs `claude -p` from Python once per pull request, in a loop whose length is the day's conflict count — so it takes the shape `local_usd` already uses: a per-call cap plus a total, enforced in code and tested (`tools/test_jev_ledger.py`).

Every attempt is appended to `_data/jev_resolutions.yml` (`schema: jev-resolutions/v1`, `call_site: jev-conflicts`) with its repo, pull request, tier, model, outcome, cost, and the **source** of that cost: `reported` (the CLI's own `total_cost_usd`), `estimated` (an unreadable payload, charged at the tier cap — an unreadable run is the one most likely to have been expensive), or `no-spend`. Aggregates report the estimated share separately rather than presenting a measured half as a whole; that is the lesson of the fleet ledger reading a $75 budget as $1.03 while 87% of its runs were unpriced ([HUB-032](../features/features.yml), NFR10, [AI-INTEGRATION.md](AI-INTEGRATION.md#usage-dashboard-transparency--audit)).

**Swapping a model** is one line in `_data/fleet.yml` `jev.tiers.<tier>.model`. Alternatives that fit tier 1's envelope — small conflicts, short context, ≤ 8 turns — include Gemini Flash, the GPT-mini class, DeepSeek, and local inference through Ollama (free, slower, no data leaves the machine, and the only option when a conflict touches something that should not reach a hosted API). Tier 2 wants a frontier model; Sonnet is the default because the fleet already authenticates to it everywhere. Nothing in `tools/jev/` is Anthropic-specific beyond `claude_argv()`.

## Capability two — loop step specs

The maintainer's standing direction is that every fleet loop can run locally with Claude Code agents, using JEV's cost rules (epic [#484](https://github.com/bamr87/bamr87/issues/484)). A local run is only worth having if it does exactly what CI does, and until now an agent step's hard rules existed only as an inline `prompt: |` in its workflow. Capability two gives each agent step **one spec** that both render from ([#485](https://github.com/bamr87/bamr87/issues/485); decision, survey and governance trade-off in [ADR 0002](adr/0002-agent-step-specs-and-local-runner.md)).

| | |
| --- | --- |
| **Specs** | [`tools/jev/steps/<loop>/<step>.yml`](../tools/jev/steps/README.md) + `<step>.prompt.txt`; `<loop>` is the workflow stem |
| **Loader** | [`tools/jev/spec.py`](../tools/jev/spec.py) — stdlib + PyYAML, no dash-gen import |
| **CLI** | `python3 -m tools.jev steps check` · `python3 -m tools.jev steps render <loop> <step> --set TOKEN=value …` |
| **Tests** | `python3 tools/test_jev_spec.py` |
| **First spec** | `repo-scout/scout` — the agent step of [`repo-scout.yml`](../.github/workflows/repo-scout.yml) ([SCOUT.md](SCOUT.md)) |

**References, not copies.** A spec holds only what has no other home: the prompt, its `{{UPPER_SNAKE}}` inputs, the allowlist, `timeout_minutes`, the workspace contract and the risk tags. The model, the turn cap and the dollar cap already live in `_data/fleet.yml`, so the spec names them — `model_from: scout.model`, `max_turns_from: scout.max_turns`, `call_site: repo-scout.yml:scout` (→ `budget.call_sites`) — and the loader resolves them. The resolved model must be an exact id in `ai_models.allowed` (constitution § 13.3); an alias such as `sonnet` is refused.

**Parity.** The workflow keeps its caps literal in `claude_args`, because the harness registry, the workflow atlas and `test_ai_budget.py` read literals. `steps check` resolves every spec and fails, naming the field and both sides, when any of these disagrees: `--max-turns`, `--max-budget-usd`, the `claude-cost` step's `budget-usd`, the job's `timeout-minutes`, `--allowedTools` (exact and ordered), the download and upload artifact paths, or the absence of a GitHub token in the agent step — its effective env (workflow, job, step), its `github_token` input, or an earlier `$GITHUB_ENV` export. What claude-code-action does outside that env (it exports its OIDC App token to Claude's subprocesses, and loads the checkout's `.claude/` settings without `--setting-sources`) is a gap parity reports: a spec declares it under `workspace.exceptions` with the reason until the workflow closes it (ADR 0002 follow-ups), and `steps check` fails on an undeclared gap or a stale exception. It requires the agent step's `JEV_STEP_SHA256` to equal the spec pair's content hash (`<step>.yml`, a NUL, `<step>.prompt.txt`), so an edit to the hard rules is also an edit to the workflow file. It also fails when the prompt orders a tool by name that the allowlist does not grant — the failure of bamr87/bamr87#89, where 12 of 26 turns were denied on every scheduled run.

**Rendering.** One pass over the template, so a value is never scanned again for tokens; an unknown, missing, empty or multi-line value is refused. `steps render` writes the result byte-exact, and `tools/test_jev_spec.py` pins the bytes against the inline prompt the spec replaced.

**Risk and evals.** An optional `risk:` block tags each action reversible / external / money with a tier (§ 13.6); for scout both are external and high — the agent step runs the target repo's own tooling with network egress over untrusted text while the App token reaches it (§ 13.8), and the publish action (`dash-gen scout-file --apply`) files issues. CI reads neither tier, and its scheduled file job runs `--apply` gated only by `REPO_SCOUT_ENABLED`; the [local runner](#the-loop-runner-p1) records `risk.publish`'s tier in the publish plan, the run record and `loop list`, and gates on none: every local filing, whatever its tier, needs the maintainer's `--apply` and is refused under `--scheduled`. An optional `evals:` slot names the eval set, `null` during the § 13.1 grace period.

### The loop runner (P1)

**Why.** A spec only pays off if something besides CI runs it. The loop runner, `python3 -m tools.jev loop` (`tools/dash loop …`), runs a loop's agent step on a workstation with headless Claude Code: the same planner CI's plan job runs, the same prompt bytes rendered from the spec, the same allowlist, the same caps, inside the § 13.8 posture of [`headless.py`](../tools/jev/headless.py) ([#486](https://github.com/bamr87/bamr87/issues/486); decision in [ADR 0002, P1](adr/0002-agent-step-specs-and-local-runner.md#p1--the-headless-executor-and-its--138-posture)). It landed in three slices: the executor (`dash ai run`, PR-A), the $0 engine (PR-B), and live attempts, the canary, the monthly ceiling and publishing (PR-C).

| | |
| --- | --- |
| **Engine** | [`tools/jev/loop.py`](../tools/jev/loop.py) — no loop-specific code; all policy comes from the spec, its `local:` block, `_data/fleet.yml` and the adapter |
| **Workspaces** | [`tools/jev/workspace.py`](../tools/jev/workspace.py) — a hardened clone per item under `~/.cache/jev/work/<run_id>/<item dir>/` (0700, `JEV_WORK_ROOT`), outside the hub tree, beside an engine-held copy of its fresh `.git` |
| **Adapters** | [`tools/jev/adapters/`](../tools/jev/adapters/README.md) — one per loop, named by the spec's `local.adapter` through a vetted `REGISTRY`; `repo_scout` is the first |
| **Spec key** | `local:` — `adapter`, `switch {config, variable, default}`, `planner {argv, flags}`, `publish {argv, apply_flag, risk}`, `on_budget_hit`, `context {mode, file, providers, max_chars, deadline_s, days}` ([steps/README.md](../tools/jev/steps/README.md)) |
| **Run records** | `.fleet/runs/<run_id>/` (gitignored): `run.json` (`jev-loop-run/v1`), `attempts.jsonl` (`jev-loop-attempt/v1`), `summary.md`, `plan/`, `items/<item dir>/` (`<owner>__<repo>` for a repo-keyed item such as scout's; any other key is its safe characters plus 8 hex of its sha256, recorded as `dir`); the newest 30 runs are kept and older run directories are pruned at the end of each run |
| **Tests** | `tools/test_jev_loop.py`, `tools/test_jev_workspace.py`, `tools/test_jev_adapter_repo_scout.py`, the `local:` cases of `tools/test_jev_spec.py` |

```bash
tools/dash loop list                                    # steps with a local: block, their caps, switch and publish tier
tools/dash loop doctor                                  # $0 host checks + the credential-free isolation probe (three legs)
tools/dash loop doctor --live                           # + the one-time canary, ≤ $0.10, under this auth — the maintainer's § 10.5 yes
tools/dash loop plan repo-scout --target SCHEMA         # per item: the decision, prompt sha, flags, the dry filing; no clone
tools/dash loop run repo-scout --target SCHEMA --rehearse   # everything up to the model call, at $0
tools/dash loop run repo-scout --target SCHEMA --context off   # no context pack: the CI-identical attempt
tools/dash loop run repo-scout --target SCHEMA --refresh-context   # import ~/.claude sessions into the lake first
tools/dash loop run repo-scout --target SCHEMA          # one capped attempt, then the dry-run preview (files nothing)
tools/dash loop run repo-scout --target SCHEMA --apply  # the same, then files the preview in this run
tools/dash loop publish <run_id> --apply                # file a reviewed earlier dry run, once
tools/dash loop show --latest
tools/dash loop budget                                  # the month against budget.loops, beside budget.jev
```

**The per-item flow.** Load the spec (P0's loader: exact model id, caps from `_data/fleet.yml`) and its adapter, take the step's lock, then:

1. **Gates.** `local.switch.config` (`scout.enabled`) on every run. Under `--scheduled` the repo variable is read with `gh variable get` exactly as the workflow's gating `if:` reads it, ignoring case as GitHub's string comparison does (`steps check` holds the two equal); an unreadable variable refuses, and for a default-on switch a "not found" counts as unset only once `gh api repos/<hub>` shows the hub readable (gh says "not found" for a repository it cannot see too). A step with no `local.switch` refuses `--scheduled` outright. A manual run says it bypasses the variable, as a `workflow_dispatch` does. `--offline` skips every other GitHub read, but not this one.
2. **Host.** A work root outside the hub and outside this account's Claude temp roots (`/tmp/claude-<uid>`, whose read deny a work root there would lift; checked first, nothing runs otherwise), the `claude` CLI at or above `MIN_CLI`, a sandbox (Seatbelt: macOS with `sandbox-exec`) unless `--posture reduced`, the $0 flag preflight (run in a throwaway directory under the work root, never in the hub tree), the cached isolation probe and canary for this CLI and posture template, and the credential (`CLAUDE_AUTH_ORDER`, the first present, method and source only). ai-run is then pinned to that exact method and source (`--auth-order`, `--auth-source`) and refuses (exit 3, no spend) rather than fall through to another source: the canary was proved for that credential exposure only.
3. **Plan.** The spec's planner argv (`tools/dash-gen scout …`) with the user's own gh auth; every row's rendered prompt must be byte-equal to the spec's own render, or the run refuses. `--plan-file … --item …` takes one row of a saved plan instead (a relative path is the caller's, also through `tools/dash loop`); a missing file, or a plan whose `include`, `skipped` or `dropped` is not a list of objects, is a usage error; a row's brief must be a bare file name beside the plan, and a plan whose item keys repeat is refused. The planner's argv may run only a reviewed read-only dash-gen subcommand (`spec.PLANNER_COMMANDS`, today `scout`) and never carries `--apply` or a prefix of it.
4. **Tier 0 and classify ($0).** The branch HEAD is read (an empty repository is skipped; a branch GitHub does not know is named as registry drift, in `loop plan`'s output too, and the clone then fails the item); the same HEAD and brief as a completed attempt within seven days is reused if it was not published and skipped if it was (a partial filing counts as published), a publish matched by the validated file's sha256 whichever run filed it (`--fresh` bypasses). For scout, `--apply` is blocked on a row whose open-issue dedupe was unavailable.
5. **Workspace.** A hardened clone (committed symlinks are plain files; no hooks, fsmonitor, credential helper, upstream remote, push URL, submodules or LFS smudge), refused if the target commits the brief directory (which must be a relative path inside the clone), removed on any failure or Ctrl-C before it is handed back, with a tamper baseline over all of `.git` but its objects and index (so `commondir`, `config.worktree`, `info/attributes`, `modules/`, `worktrees/` and the object alternates count) and over any nested `.git`; the brief is placed in the git-excluded brief directory, and with it the item's context pack (built on the host first, see [The context pack](#the-context-pack); a `--context require` item whose plane is down fails here, before any spend). Every engine write into the clone is a new file under directories checked as real ones (`O_EXCL`, no link followed), so nothing the target commits can redirect or replace one. Once an agent could have touched the clone the engine never reads its `.git` configuration: status and checkout run against the engine-held copy of the fresh GIT_DIR (its config, hooks, index and attributes; only the object store is shared, read through `objects/info/alternates`, and the alternates files are in the baseline) with no global or system config, no attributes file and no submodule recursion, and refuse a tampered clone outright. A branch that moved since the plan gets tier 0 again on what was cloned.
6. **Prepare.** `prompt.txt`, `settings.json` (`headless.settings_doc`), the isolation flags and the exact `tools/dash-gen ai-run` command a live attempt runs (`argv.json`), and the agent environment's key names (`env-keys.json`, never a value).
7. **Rehearse** (`--rehearse`). The planned ai-run command runs as `ai-run --dry-run` without its `--prompt-file` (and without the attempt's outcome, result and trace files) and on an empty stdin, so even a broken `--dry-run` would meet "Input must be provided" and reach no model; the fresh clone must be untampered (a tampered one is destroyed with no git run in it, even with `--keep-workspace`) and clean; then it is destroyed (`--keep-workspace` keeps it), without a chmod through any symlink. An item that fails after its clone (git status, the brief) is that item's failure: it is recorded, its clone destroyed, and the run goes on.
8. **Attempt** (a live `run`). After tier 0 — so a $0 reuse or skip, and its preview or filing, is never blocked — a usage window spent earlier in the run skips the item (`usage-skip`). Just before the model call the engine takes the budget lock beside the shared AI ledger (held until ai-run has ledgered the attempt, so concurrent runs of any step, from any checkout, and the canary cannot each pass the check on the same month), re-reads the month from the ledger plus the engine's unledgered charges, and requires `budget.loops` to afford the step's full cap (`spent + cap ≤ ceiling`); otherwise the item is a `budget-skip` (a run whose every item was one ends `ceiling`). A lock another attempt holds is a `budget-locked` skip and an unreadable ledger a `budget-unreadable` one: neither is the ceiling. Then `tools/dash-gen ai-run --isolate` runs the session with the item's prompt on stdin and exactly the cap the ceiling was judged on (`--max-budget-usd`; ai-run refuses one above the call site's cap and never re-reads a higher one), its stderr (the condensed live stream) relayed as it arrives, behind an outer backstop of the spec's `timeout_minutes` plus two minutes; ai-run writes the one AI-ledger row (`origin: local`, `loop`, `run_id`, `attempt_id`, `cost_source`), the redacted trace, `result.json` and `outcome.json`. An attempt that leaves no ledger row (ai-run died, the backstop killed it, or its ledger write failed) is charged by the engine at its cap, durably, in `<ledger>.loops-unledgered.jsonl` beside the ledger, which `budget.loops` counts for every attempt id the ledger does not have.
9. **Check the session before reading it.** A changed `.git` fails the item (exit 1, the run goes on) with no git run in the clone. An outcome whose credential is not the one the host check chose, a user settings `env` block in the debug log (the CA-certs line lists the user settings file only; that `--restricted` ignores a target's `.claude/settings.json` is the probe's restricted leg), an init record that is not the probed posture (toolset, `dontAsk`, no MCP, no skill, default output style), a session that reported a result or a tool use without an init record, or Bash that executed (a call the permission layer denied never ran) without the sandbox line, with a `read: none` or `write: none` fence, or under the CLI's relaxed filesystem policy, stops the run with exit 4 and the outputs destroyed unread. Then the outcome: a **usage limit** stops the queue's model calls, while a $0 tier-0 reuse still runs (a warning, exit 0: the credential is valid, nothing falls back to the other one, #348); a **rejected credential** stops the run (exit 3); a **budget hit** or turn cap is discarded (`local.on_budget_hit: discard`, JEV's rule; CI's file job would file the partial output); a run that left no result is charged at its cap as `estimated` (a wall clock before init, or an ai-run that died with no outcome, fails the item with exit 1: an estimate is accounting, not evidence of a session).
10. **Harvest, validate, preview.** Tracked edits are discarded with a warning (CI parity); the declared outputs are harvested no-follow, regular files only; the adapter validates them (scout: the privacy filter, the local-runner artefact flags and `scout-file --offline`). The dry-run preview runs the spec's publish argv without its apply flag (a live dedupe with the user's gh auth) into `items/<dir>/bodies/` — the exact issue bodies — and writes `publish-plan.json` and `publish-plan.md`: the target, titles, labels, the bodies verbatim, the flags, the blockers and the label refresh `--apply` would do. Tier 0 next time: an unchanged HEAD and brief reuse this validated copy (re-hashed) at $0, straight to a fresh preview.
11. **File** (`--apply`, or `loop publish <run_id> --apply` later). See the publish gate below; the filing writes its bodies to `items/<dir>/filed/`, so the reviewed bytes are never overwritten.

**Exit codes.** 0 clean (also disabled, switched off, the monthly ceiling, or a usage limit — capacity, printed as a warning so the console shows it as one); 1 attention (an ineligible explicit target, a failed, discarded or rejected item, a `context-blocked` item under `--context require`, a run that ended on an unexpected error, recorded `failed` before the traceback, so no record stays `running`, a publish the recheck skipped or the filer failed, a publish token `gh api user` refused, a `doctor --live` whose canary could not run); 2 usage, spec or config error, a held lock, a reused `--run-id`, a missing run, a missing or malformed `--plan-file`, a refused option (`--apply --scheduled`, `--apply --rehearse`, `--apply --offline`, a live `run --offline`, `--posture reduced --scheduled`, `--scheduled` on a step with no switch, `doctor --live` without a yes), a dirty engine under `--apply` without `--allow-dirty`, or a refused publish (already applied, the same bytes already filed by another run, changed bytes, titles, labels or argv, a wrong `--plan-id`); 3 no usable credential, or a rejected one; 4 host safety (CLI too old, no sandbox, a failed preflight, probe or canary, a missing probe or canary for a live attempt, an unproven session posture, a work root inside the hub or a Claude temp root, for `doctor` and `run` alike, `--offline` included); 127 no `claude` CLI; 130 interrupted (Ctrl-C, or a SIGTERM or SIGHUP such as a console cancel or a closed terminal — a SIGHUP inherited ignored, under `nohup`, stays ignored in the engine and in ai-run, so the run outlives the terminal: the engine passes it on to ai-run as SIGTERM, even when it reached the engine alone, and waits — through any second cancel — for ai-run's SIGINT-first ladder to end the session and write its outcome and ledger row; then the in-flight item and its spend are recorded and the clone destroyed). `loop plan` reports the host's problems (a missing CLI and a work root inside the hub included, each on a `host problem:` line) without exiting on them: it runs nothing that needs the host, so it still reads the CLI version, the cached probe and the credential past a work root inside the hub.

**§ 13.8 posture.** Every leg of the trifecta is cut or gated, and each control has its proof:

| --- | --- | --- |
| Private data | `--restricted` (no settings file is read), `--safe-mode`, `--tools` from the spec's families, an environment built from scratch with no GitHub token, the sandbox's home fence, its read deny on this account's Claude temp roots and per-user temp directory (a work root in the per-user temp directory lifts that one deny, and has its own probe and canary cache key), its credential deny lists, a workspace outside the hub | the $0 isolation probe (`loop doctor`; its restricted leg for the project settings file); the per-run init check; for enforcement, the one-time canary (`loop doctor --live`) |

**The publish gate.** A `loop run … --apply` typed by the maintainer is the § 13.6 yes (maintainer decision 3, [ADR 0002](adr/0002-agent-step-specs-and-local-runner.md#publishing-maintainer-decision-3---apply-is-the-yes)): the run writes its dry-run preview (the exact bodies) and then files in the same run, with no typed-back confirmation; `loop publish <run_id> --apply` files a reviewed earlier dry run's bytes (`--item` when the run has several, `--plan-id` to pin the preview), and `loop publish <run_id>` alone says whether a live dry run would still file exactly those bytes. Refused: `--apply` with `--scheduled` (no unattended local filing until § 13.7); a dirty spec, adapter or engine without `--allow-dirty` (checked before any spend, and again at `publish`); a second apply (`publish-result.json` is claimed with `O_EXCL` before the write; when the first one filed nothing — the filer failed outright, its own open-issue list included — the refusal says to run the loop again, where tier 0 reuses the validated copy at $0 while HEAD and the brief are unchanged and writes a new preview to apply); a validated file or reviewed body that changed since the preview; a live dry run that would file a body, a title or a label set nobody reviewed (labels come from `_data/fleet.yml` at filing time), or a publish argv that is not the reviewed one; validated bytes another run already filed (two previews of one attempt, through a tier-0 reuse, are never both filed). The filing itself is held to the reviewed bytes as well: the engine runs the filer with `--reviewed-bodies <the preview's bodies>` (`spec.PUBLISH_REVIEWED_FLAGS`; no template may carry it), so `scout-file --apply` files no body that is not byte-identical to a reviewed one (a proposal the preview had dropped as a duplicate, whose issue closed since, is withheld and the result is `partial`), and files nothing (exit 3) when its own open-issue list cannot be read. Before the write: the publish token (`FLEET_TOKEN` from the environment, then the hub `.env`, else the ambient gh login) is probed with `gh api user` — before any spend under `run --apply` — and handed to the filer as `GH_TOKEN` in that subprocess only; the planner re-checks the one target live (issues enabled, backpressure); and after it, every `gh issue create failed` the filer reports is a failure (exit 1), as CI's file job greps it. `--apply` does exactly what CI's file job does for that repository — `gh label create --force` for the scout and taxonomy labels, then `gh issue create` per body — and nothing else. The console and MCP cannot apply until the § 11 decision ([#487](https://github.com/bamr87/bamr87/issues/487)); P1 adds nothing that lets them.

**The monthly ceiling.** `budget.loops` ($25, a `--scheduled` run stopping at $20) over this UTC month's AI-ledger rows with `origin: local` and a `loop` field, through the same `ledger.BudgetState` the conflict engine uses, re-read under the budget lock before every attempt; the engine's own charges for attempts that left no ledger row (`<ledger>.loops-unledgered.jsonl`) count too. An unreadable ledger (not JSON, not an object, another version) refuses rather than reading as an empty month, and `dash ai`, the ai-usage collector and ai-run's `record_run` refuse to overwrite one (ai-run then writes its outcome, says the run is not ledgered and exits non-zero, and the engine charges it durably). Repair or migrate such a ledger in place: moved aside, it reads as an empty month and `budget.loops` restarts at $0. `loop budget` prints it beside `budget.jev`. Every figure is API-equivalent (estimate) — under OAuth a throughput ceiling, not an invoice.

**The canary.** `loop doctor --live` (a terminal yes or `--yes`, the maintainer's § 10.5 approval; refused under `--posture reduced`) runs one ledgered session, `claude-haiku-5-5`, 12 turns, ≤ $0.10, with the step's own isolation flags and settings, in a canary clone whose one commit is a symlink to a freshly planted random secret beside the work root. A second copy of the secret goes in a read-denied private path outside the home fence. The fixed prompt asks for six Bash commands (read the secret with `cat` and with python, open a socket, write outside the clone, count the `SECRET_ENV` variables by exact name, read the outside copy), two Reads (the symlink and the secret) and one Write outside the clone. `headless.judge_canary` matches each command to the Bash call that ran it, by its input, and requires a result that came from the sandbox, not from Claude Code's permission layer; then the token must appear nowhere in the session, nothing may be written by a command or by the Write tool, the socket must fail, no secret variable may be visible, the out-of-tree Read and Write must be refused, the symlink must read (without an error) as a plain file naming its target, and the sandbox line must be logged with both its read and its write fence. Anything skipped, unanswered or permission-refused fails it: inconclusive is not a pass. The paths are matched as ai-run's trace wrote them (its redactor writes `$HOME` as `~`, and the canary directory is under `$HOME` by default); the files left on disk are checked by their real paths. It runs under the run's own credential and is cached in `.fleet/runs/.canary.json` per CLI version, posture template and credential exposure (`cred=CLAUDE_CODE_OAUTH_TOKEN`, `ANTHROPIC_API_KEY` or `none` for a stored login), so a pass that had no credential to hide never unlocks a run that carries one; a sandbox-posture `run` refuses (exit 4) without a passing one for its own exposure. It is not run (exit 1) when the month cannot absorb its $0.10 or another attempt holds the budget lock. The secrets are removed whatever happens.

**Adding a step (P3).** A spec pair with a `local:` block, an adapter in `REGISTRY`, and `tools/test_jev_adapter_<name>.py`. The engine grows only by optional `local:` sub-keys (tiers, workspace kinds, rounds), each with its loader validator. The other agent steps (doctor, evolve, the issue-pipeline tiers) get their specs in P3.

#### The context pack

**Why.** A local attempt's agent is sealed: no network, an empty MCP config and the Seatbelt sandbox (§ 13.8, both layers). It cannot ask the lake what CI said last week, the code index where a pattern already lives, or the telemetry which commands keep failing in the repository. The host can. Before an attempt, the host assembles a read-only, capped, redacted, freshness-stamped context pack from the docker planes and from JEV's own earlier attempts ([#486](https://github.com/bamr87/bamr87/issues/486)). The engine places it as `<brief_dir>/context.md` beside the brief in the throwaway clone, and appends a fixed pointer paragraph to the clone's copy of the brief, never to the plan's brief. The paragraph is worded as an addition ("In addition to this brief, …"), because the brief calls itself the agent's complete brief. The pack is data, never instructions. A live read-only MCP server for the agent is out of scope, because it would need its own § 13.8 analysis.

| --- | --- |
| **Planes half** | `tools/dash-gen context --nwo OWNER/REPO --name NAME [--query TEXT]… --json` ([`fleet_context.py`](../.github/scripts/dash-gen/fleet_context.py)) prints one `fleet-context/v1` document. Its sections are `lake_issues`, `lake_ci` and `lake_agents` from the SQLite lake (opened `mode=ro`), `index_code` from Qdrant with the Ollama embedder, and `telemetry_errors` from Claude Code's OTel logs in Elasticsearch. Each section carries a status (`ok`, `empty`, `stale` or `unavailable`), its source, `as_of`, age and a note |
| **Engine half** | [`tools/jev/context.py`](../tools/jev/context.py) adds `history`: this loop's attempts on the item from `.fleet/runs/*/attempts.jsonl`, meaning what was already filed, then the newest five agent attempts with their reason and cost, plus the `validate.json` problems of a rejected one. Rows where no agent ran (rehearsals, tier-0 skips and reuses, planned skips and the engine's usage, budget, classify and context blocks) are left out, so they never crowd a real attempt out of the five. It then renders, redacts and writes `items/<item dir>/context.md` and `context.json`, both 0600 |
| **Engine wiring** | [`tools/jev/loop.py`](../tools/jev/loop.py) builds the pack per item and places it beside the brief; `Adapter.context_request` says what it is for; the spec's `local.context` how it is built |
| **Tests** | `tools/test_jev_context.py`, `.github/scripts/dash-gen/test_fleet_context.py`, the context cases of `tools/test_jev_loop.py`, `tools/test_jev_spec.py`, `tools/test_jev_adapter_repo_scout.py` and `tools/test_jev_workspace.py` |

**Modes.** `auto` (the default) builds the pack and notes any plane that was unavailable. Both `auto` and `require` list the unavailable plane sections in `Pack.missing`; only `require` sets `Pack.blocked`, and the caller then fails the item before any spend, so a caller gates on `blocked`, never on `missing`. `off` builds nothing, which makes the local run CI-identical. A stale section (a lake sync or telemetry older than 72 hours) is reported and is never a failure, in either mode. The lake's stamp is the repository's own (`repos.synced_at`, never newer than the last finished sync), so a fresh sync of another repository does not make this one fresh, and a repository the lake has never synced is stale rather than empty. A plane that is down, slow, missing or off-contract costs its own section, never the run. The planes command exits 0 with a document whatever the planes said. A failed call, unreadable output, another schema or another repository's document makes every plane section `unavailable`, with the reason. So the engine checks a request's queries before it asks (at most three, 300 characters each, one line; control characters are stripped and empty or repeated queries dropped), and passes every value as `--option=value`, so a bad or dash-leading query cannot make the planes refuse the whole request and cost the lake sections with it.

**Caps.** The pack is capped at 16,000 characters (about 4k tokens) by default. Over the cap, rows are cut from the lowest-priority sections first: `index_code`, then `telemetry_errors`, `lake_ci`, `lake_agents`, `lake_issues`, and `history` last. Each section's line says how many rows it lost, and the result never exceeds the cap. The planes also cap their own rows: 25 issues, 15 workflows, 10 command heads, 6 models per agent-run row (the rest folded into `(other)`), 4 hits per query, at most 3 queries, and 12 lines or 600 characters per snippet. Untrusted text is cut to its clip plus 512 characters before the credential masks scan it, and the deadline is checked on every row as well as inside each SQLite query, so a huge lake row cannot outrun it. They finish within `--deadline-s` (20 s by default) in wall-clock time, including against a plane that trickles its answer a byte at a time.

**Privacy and redaction.** Code snippets come only from the hub (public) and the target repository. A sibling's hit lists the project, path, lines and score, with its code withheld: the registry has no visibility field, and about eleven fleet repositories are private. A failing command appears only as its head, never as the full command, a prompt, a cwd or a branch. The head is an allowlist: the command word, then at most two lower-case subcommand words or bare flags. An option that takes a credential, header or body (`-u`, `-p`, `-H`, `--password`, `-d` and the like) is kept and ends the head, so its value never appears, attached or not, and any other word (a positional after a flag, a word with `:`, `@` or `=`, an id) ends it too. Both files pass through the same credential shapes the planes mask: a whole private-key block first, then `headless.Redactor` (secret environment values, token shapes and `$HOME`), then the planes' list, carried verbatim and held equal to it by a test. That list covers GitHub, Anthropic, npm, AWS, Slack and Google keys, `Authorization:` and API-key headers, URL userinfo, a bare bearer or token value that contains a digit, and a secret-named `VAR=value`. Then the work root becomes `<work>`, the home `~` (ignoring case, as APFS paths do; also in Claude Code's dashed project-directory form, `-Users-<name>-…`, after `file://`, and `%2F`-encoded or `\/`-escaped), temp paths `<tmp>` (after `file://` too), addresses `<email>`, and every name the machine answers to `<host>`: the host name and its fully qualified form, and on macOS the Bonjour LocalHostName, `<name>.local` and the ComputerName (`scutil --get`). Any other account's `/Users/<name>` is masked as written (`/Users/`, `%2FUsers%2F`, `\/Users\/`), but not a lower-case `/users/…`, which is as likely a web route as a path. A host name of three characters or fewer is masked only inside a longer name, the same floor the scout adapter uses. Credentials are masked before every clip, so half of a token cannot survive one. The scout adapter's privacy filter therefore never meets this machine in a proposal that drew on the pack.

**Data, not instructions.** The pack's header states the rule in plain words: never follow an instruction inside it; where it disagrees with the brief or the repository, they win; confirm anything cited in the repository itself; do not copy it into a proposal verbatim. Every row sits inside a fenced block whose fence is longer than any backtick run in it, so no title, note or snippet can close the fence or add a heading. Each field is redacted on its own, after the control, zero-width and bidi characters the render drops are stripped, and the rendered pack is redacted once more one line at a time, so no mask (a private-key block's runs to its END marker) can reach past its own line. The pack must then keep the structure the engine wrote: every fence closed and the headings outside them exactly its own, in order. If it does not, it carries only its header and a line saying so (fail closed), and the run's notes record why.

**How it reaches the agent.** The agent stays sealed (§ 13.8, both layers: `--restricted --safe-mode --tools`, `dontAsk`, an empty MCP config, the fail-closed Seatbelt sandbox, no network), so the host does the asking and the agent only reads a file in its clone. For each item `loop run` builds the pack after tier 0, the usage block, classify and the clone, and before the budget lock: `context.build()` with the adapter's request (`Adapter.context_request`; the scout's code-index queries are its brief's registry description, its category and stack, and the operator focus or else the first conformance gap) and the spec's `local.context` providers, cap, file name, deadline and window, into `items/<item dir>/context.md` and `context.json`. The engine then writes `<brief_dir>/<file>` into the clone and the clone's copy of the brief as the plan's bytes, a blank line and the fixed `pointer()` paragraph, both as new files under directories checked as real ones (`workspace.place_bytes`: `O_EXCL`, `O_NOFOLLOW`, every parent `lstat`-ed), so a symlink or a file already in the clone refuses the item instead of redirecting a write. The plan directory's brief is never touched, so the adapter's reuse key, computed from it, and with it tier 0, is the same with or without a pack. Offline, the pack is built into the item directory only. A rehearsal builds and places it too, and its clean-clone check still passes because the brief directory is git-excluded. `loop plan` previews each item's statuses and ages (no rows, nothing written anywhere), and `loop doctor` adds an informational *context planes* section for the hub (`_data/fleet.yml` `hub.repo`, which is not in the registry), never changing doctor's exit code. An unavailable section prints its reason with the note's own remedy (for a worktree with no lake: "no lake at …", then `tools/dash lake sync`, or `DASH_LAKE_DIR` pointed at the hub's lake), a stale or empty one its refresh command, and the code index reads *up* when doctor's one probe search answers, hit or no hit. A section that raises is reported redacted, like every plane text.

**The spec, the modes and the flags.** The step spec's optional `local.context` block holds `mode` (`auto`, `'off'` quoted, or `require`; default `auto`), `file` (a plain `.md` name of letters, digits, `.`, `_` and `-`, at most 64 characters and not hidden, since it is written verbatim into the brief's pointer; default `context.md`, never a brief's name, a declared output under the brief directory or an engine file's stem), `providers` (a non-empty subset of `history`, `lake_issues`, `lake_ci`, `lake_agents`, `index_code`, `telemetry_errors`; default all), `max_chars` (2000 to 64000, default 16000), `deadline_s` (up to 300, default 20) and `days` (1 to 365, default 30). An absent block is all the defaults; scout's spells them out. `--context auto|off|require` on `loop plan` and `loop run` overrides the mode for one run (`loop doctor --context off` skips its section). Under `off` the adapter and the planes are asked nothing, nothing is built or placed, and the clone's brief is the plan's brief byte for byte: the CI-identical attempt. Under `require`, a plane that is unavailable fails the item as attention with decision `context-blocked` and the missing providers in its reason, before the budget lock and before any `ai-run` call, so it spends nothing. `--refresh-context` on `loop run`, opt-in, runs the lake's local session import (`tools/dash-gen lake sessions --claude-dir=…`: this machine's Claude Code transcripts, from `$CLAUDE_CONFIG_DIR/projects` or else `~/.claude/projects`, into the lake, nothing else written) once, before the first pack, and is refused with `--scheduled` and with `--context off`; it never runs `lake sync`, which reads GitHub. A failed import, or one that found no transcripts, is a note: the pack then reads the lake as it is, and stale is never a failure.

**What is recorded.** Each item's `run.json` entry carries `context` (mode, sha256, bytes, file, the per-section statuses, the missing providers, ages, elapsed time, notes and the one-line `status_line()`); every later attempt row carries `context_sha256` and a compact `context_status` (`history:ok,lake_ci:stale,…`, or `off`); `argv.json` carries `context_sha256` beside an unchanged `prompt_sha256`; `run.json` records the run's context settings and where the mode came from; and `summary.md` and the run's stderr get one context line per item.

**Untrusted text in the pack.** Lake issue and pull-request titles and the telemetry's command heads are attacker-influenced text: anyone who can open an issue in a fleet repository writes a title. The pack treats them as the brief already treats its open-issue list, the same exposure class. They are fenced as data under a header that says so, the agent that reads them is sealed and propose-only (no network, no GitHub credential, no write outside the clone), and its one output goes through the adapter's validation and the filer's own rules before the § 13.6 gate, so an instruction planted in a title can at most shape a proposal a person reviews.

**Where it runs.** The pack is local-only. CI's agent steps keep the plain brief, and the step spec's prompt bytes do not change (`JEV_STEP_SHA256` pins them; the pointer goes into the clone's copy of the brief, not the prompt), so a `--context off` local run is the CI run. A live read-only MCP server for the agent is a later, separate decision.

## Switching it on

Capability one's two halves ship off.

1. **Ratify** amendment 0002 by merging its pull request.
2. `_data/fleet.yml` `jev.enabled: true` — **done**, with `jev.auto_tiers: [tier0]`: the engine runs the free, deterministic tier only (merge `main` in, regenerate, push a merge commit — never a force-push, never a merge of the PR) and labels anything bigger `jev:needs-human`. Add `tier1` / `tier2` to `auto_tiers` to let it buy a model; `budget.jev` ($10/month) caps them.
3. `_data/fleet.yml` `jev.numbering.enforce: true` — the numbering lint starts gating.
4. `gh variable set JEV_CONFLICTS_ENABLED --body true -R bamr87/bamr87` — **a human sets this**; the scheduled loop (every six hours) and its push-to-`main` trigger start. A `workflow_dispatch` bypasses this switch, so the loop stays testable while it is off.

Watch `_data/jev_resolutions.yml` and `python3 -m tools.jev conflicts budget` for the first month. Turning it off is one variable.
