# bamr87 — Constitution

> The rules every change to this repo must satisfy, whoever makes it — a human or an AI agent.
> Agents read this before [AGENTS.md](../AGENTS.md) conventions, the [PRD](../PRD.md), or the
> [feature catalog](../features/features.yml). Ratified by merged PR; amended only per § 8.

## 1. Mission

The `bamr87/bamr87` repo is simultaneously the GitHub profile README, the fleet control plane ("dash") that vendors every project as a Git submodule, and the public Harness Console site. It hosts shared standards, kits and reusable actions (e.g. `claude-run`) that the rest of the fleet consumes.

_Source: [PRD.md](../PRD.md)._

## 2. Invariants (non-negotiable)

These rules are lifted from the repo's own agent guide; breaking one is grounds to reject a PR.

- `_data/projects.yml` is the project registry; `.gitmodules` must agree on submodule paths, URLs, and branches. _(AGENTS.md)_
- Never commit a lockfile. _(CLAUDE.md)_
- Don't suppress type errors (`as any`, `@ts-ignore`, `# type: ignore`) or leave empty exception handlers. _(CLAUDE.md)_
- Add/remove/rename files in the nearest `SCHEMA.md` in the same change. New directories need their own schema and a parent Structure row; follow `Placement` and `Forbidden`. _(AGENTS.md)_
- The Pages build runs under `/bamr87/`, so every in-app link goes through React Router's `basename` and every file URL through `asset()` (`web/src/api/backend.ts`) — never a bare `/path`. _(AGENTS.md)_
- Overrides live in the hub's `.fleet/compose/`, never in submodules. _(AGENTS.md)_
- Branches: all track `main`. Read the branch from `.gitmodules`; don't assume. _(CLAUDE.md)_
- Don't bundle changes across multiple submodules into one PR. _(CLAUDE.md)_
- Secrets (tokens, API keys) are never printed, logged or committed. _(fleet rule)_
- `CHANGELOG.md`, when present, is not hand-edited once release-please owns it. _(fleet rule)_
- A pull request never assigns a sequential id. New entries carry a placeholder (`HUB-NEW`, `FR-NEW:<key>`, `NFR-NEW:<key>`, `number: NEW`) and reference each other by slug; the number is assigned on the default branch, by one serialized process, and is never reused. _(amendment [0002](amendments/0002-conflict-free-numbering.md))_
- A generated file is never hand-merged. A file generated end to end that is marked `jev-main-only` in `.gitattributes` is regenerated and committed only on the default branch, by the post-merge job, and CI fails a pull request that edits it. A generated span in a hand-written file is regenerated by the same job, and a pull request's drift check on it is advisory. Every other generated file is resolved by regenerating it, and CI fails on drift rather than trusting the resolution. _(amendment [0002](amendments/0002-conflict-free-numbering.md); amendment `generated-files-main-only`, numbered at merge — see the [amendment log](amendments/README.md))_
- Every scheduled or AI-calling workflow has a kill switch whose state is managed centrally in `_data/fleet.yml` `switches:`; nothing pauses or resumes a loop except through that map. _(amendment `central-loop-switches`, numbered at merge — see § 17 and the [amendment log](amendments/README.md))_

## 3. Authority and precedence

When two documents disagree, the higher one wins and the lower one is fixed in the same PR:

1. This constitution (and its ratified amendments in [docs/amendments/](amendments/))
2. [AGENTS.md](../AGENTS.md) — how to work here (commands, conventions, Definition of Done)
3. The PRD ([`PRD.md`](../PRD.md)) — what the product must do (requirement ids `FRn` / `NFRn`)
4. [features/features.yml](../features/features.yml) — what it does today (stable feature ids)
5. ADRs in [docs/adr/](adr/) and specs — why and how a specific change was made
6. Code, tests, generated files

## 8. Amendments

This constitution changes only through a numbered record in [docs/amendments/](amendments/) (`NNNN-kebab-slug.md`, compiled from a proposal in [docs/amendments/proposed/](amendments/proposed/)):

1. **Propose** — open a PR that adds the record as `docs/amendments/proposed/<kebab-slug>.md` with `**Number:** NEW` (copied from [0000-template.md](amendments/0000-template.md)) *and* the edit to this file it describes. Name what it affects: constitution sections, PRD requirement ids, feature ids. The number is assigned when the PR is merged, by `tools/jev/number.py` (amendment [0002](amendments/0002-conflict-free-numbering.md)); a record that has been numbered is append-only history and is never renumbered.
2. **Review** — the maintainer reviews; an agent never approves or merges its own amendment.
3. **Ratify** — merging the PR ratifies it. The record says `Status: ratified` and `Ratified by:` the PR. A rejected or withdrawn PR keeps its record with that status; numbers are never reused.
4. **Supersede** — a later amendment may replace an earlier one; mark the old record `superseded by NNNN`.

Records are append-only history: fix a ratified rule with a new amendment, never by editing an old record. [0001](amendments/0001-ratify-constitution.md) ratifies this document; [0002](amendments/0002-conflict-free-numbering.md) moves id assignment to merge.

## 9. Work tracking

GitHub Projects (v2) are the system of record for work across the fleet ([amendment 0003](amendments/0003-github-projects-work-tracking.md), [plan](PROJECTS-FRAMEWORK.md)):

- One **Fleet Portfolio** project holds every open issue and PR of every registry repo; **domain projects** hold a subset. Projects, fields, options, lifecycle and the label map are defined only in [templates/projects/framework.yml](../templates/projects/framework.yml).
- Required fields: Status, Priority, Area, Repo; plus Feature ID (`HUB-NNN`, a `features.yml` id) and PRD req (`FRn`/`NFRn`) when the item changes a feature or a requirement.
- Status lifecycle: Inbox → Triaged → Ready → In progress → In review → Done, with Blocked and Won't do. Labels mirror fields; the project wins on conflict.
- Agents read and move items only through the console MCP layer or the sync workflow.

## 10. DevOps methodology

Every human, bot and AI agent in the hub and every submodule under `projects/` follows this methodology (amendment `projects-devops-methodology`, numbered at merge — see the [amendment log](amendments/README.md); extends § 9 and [0003](amendments/0003-github-projects-work-tracking.md)):

1. **Everything is an item** — every feature, fix, audit and plan, including AI-agent and submodule work, is an issue or PR on the shared [Fleet project](https://github.com/users/bamr87/projects/14) (user project #14).
2. **Epics for multi-phase work** — an `epic` issue with one linked sub-issue per phase, in order, each with scope, acceptance criteria and guardrails.
3. **Hub labels** — `epic` (purple `#6E40C9`, created if missing); type `bug`/`feature`/`chore`/`docs`/`ci`/`refactor`/`test`; priority `P0`–`P3`; existing `size:*`.
4. **Fields set** — Status and Priority on every item.
5. **Hands off the Mac** — nothing running on Amr's Mac (checkout, containers, live jobs, monitoring stack) is modified until a final deploy step that Amr explicitly approves.
6. **Read-only tools** — new tools are read-only by default, with allowlists, result caps, time limits and redaction.
7. **Honest cost** — every AI cost figure is labelled "API-equivalent (estimate)"; real metered API spend is tracked separately.
8. **Prior art first** — every new harness or loop design (a new loop, harness, agent pipeline, or console surface that drives or visualizes them) includes, before implementation begins: (a) a **needs assessment**, (b) a **prior-art / existing-tools survey** with one line each on fit, and (c) a recorded **build-vs-adopt decision** with reasons, kept in the design issue or spec as an acceptance criterion (amendment `harness-prior-art-research`, numbered at merge).

## 11. Harness write-back to GitHub

The console may write to GitHub Projects (v2), issues and pull requests across every registry owner (amendment `projects-write-back`, numbered at merge; extends § 9 and § 10.6), only under these rules:

1. **Allowlist** — only the mutations listed in `tools/console/gh_projects_write.py` `ALLOWLIST`: create or update a project and its fields; add, move, set or clear fields on, archive and unarchive items; edit title and body, labels, assignees, milestone, open/closed state and sub-issues of issues; edit title and body, labels and draft state of pull requests. Anything else is refused.
2. **Never** — merge, delete, transfer, repo or org settings, branch protection, rulesets, secrets, workflows, webhooks, collaborators or visibility, even with every flag and confirmation set.
3. **Off by default** — writes need `HARNESS_PROJECTS_WRITES=1`; MCP write tools also need `HARNESS_MCP_ALLOW_WRITES=1`.
4. **Dry run, then confirm** — every change is first a plan (before → after, deterministic `plan_id`); it is applied only with `confirm=true` and the same `plan_id`, after a human has seen it; a plan whose targets changed since the preview is refused.
5. **Idempotent and capped** — already-satisfied ops are no-ops; at most 50 ops per plan and 200 per hour.
6. **Audited** — one append-only JSONL record per op (who, when, plan, before, after, result), token values redacted.
7. **Scoped token** — a dedicated `PROJECTS_TOKEN` (`read:project`/`project`, `read:org`, issues and pull requests read/write on registry repos), held in the console's credential store or an Actions secret, never printed or committed; only Amr provisions it.

## 13. Eval baseline and risk tiers

_(amendment `eval-baseline-risk-tiers`, numbered at merge — see the [amendment log](amendments/README.md); follows § 12 of `agent-merge-review-gate`; extends § 10 and § 12)_

1. **Eval set** — every bot or agent role and every repo harness or loop keeps about 20 real past tasks (input, expected output, pass criteria, optional LLM-judge rubric), versioned next to what it tests; existing harnesses and loops have a grace period until their spoke fan-out PR lands.
2. **Rerun on change, required check** — rerun after any prompt, tool or model change; an eval regression is a required CI check, so a failing run makes the PR not mergeable (§ 12.1).
3. **Pinned models** — exact versions, never aliases, from the list in `_data/fleet.yml` `ai_models.allowed`; changing it is gated (§ 12.3).
4. **Cheaper only if green** — a step moves to a cheaper model only if its evals still pass.
5. **Tracing** — every run records its tool calls, secrets redacted.
6. **Risk tiers** — every tool or action is tagged reversible / external / money and tiered: low runs alone; medium runs with an audit record; high waits for Amr's yes. Irreversible, external or money actions start high.
7. **Earned autonomy** — one tier down per action only after N consecutive clean approvals (N = 25); any rejection resets to high; money never goes below high.
8. **Lethal trifecta** — private data + untrusted content + external send always needs a human gate on the send.
9. **Reconciliation** — draft-before-send stays; only Amr merges amendments; no agent approves its own action or changes its own tier; tier changes are gated under § 12.3.
## 12. Merge authority and the review gate

_(amendment `agent-merge-review-gate`, numbered at merge — see the [amendment log](amendments/README.md); amends § 4)_

1. **Mergeable PR** — a pull request is *mergeable* only when **all** of these hold, rechecked against live GitHub state immediately before the merge:
   1. every required CI check is green;
   2. every required review is satisfied;
   3. it has no merge conflicts with its base;
   4. the review gate (item 3) has passed wherever human review is required.
2. **Agent merge** — an AI agent may merge a PR only when it is mergeable; otherwise it waits. It merges with a merge commit (never squash or rebase), never with `--admin` or any bypass, and never by force-push.
3. **Review gate** — a PR needs human review, and is gated, when it touches any of: amendments, this constitution or a fleet standard; secrets, tokens, budgets or billing; repo or org settings, branch protection, rulesets or permissions; security-sensitive code or config; deploys or anything that changes the maintainer's machines; a non-trivial conflict resolution; destructive or data-deleting changes; anything labelled `agent:hold`, `blocked` or `needs-amr`; and any repo-specific content gate its own constitution names (for example an editorial charter for structural changes).
4. **Gate mechanism** — a gated PR carries the `needs-amr` label and its Fleet project item is set to status *Needs Amr* (§ 9). The gate passes only when the maintainer approves or merges it and the label is removed by the maintainer. A repo may also require a review in branch protection; only the maintainer turns that on.
5. **Never** — an agent never merges a gated PR, and amendments are ratified only by the maintainer merging them (§ 8).
6. **Fleet conformance** — every repo constitution under `projects/` conforms to this section or files its own amendment saying how it does.
## 14. Public documentation site

_(amendment `public-docs-site`, numbered at merge — see the [amendment log](amendments/README.md); section number contingent on § 12 from `agent-merge-review-gate` (#481) and § 13 from `eval-baseline-risk-tiers` (#482) landing first; extends UPS-DOC)_

1. **A public site** — every fleet repo publishes a public site at `<owner>.github.io/<repo>` (a custom domain on that Pages site is compliant) with all its documentation (README, AGENTS.md, CHANGELOG, `docs/`, plus the PRD, feature catalog, constitution and amendments where they exist). 3. **Private repos** — they fail the check and are flagged for Amr; an agent never makes one public, and their Actions spend stays $0.
4. **Conformance** — `tools/conformance.py` (via `check-drift.sh`) checks that the site exists, uses the zer0 theme, has a complete docs index and has links that resolve.
5. **Rollout** — the check is warn-only for a repo until its spoke fan-out PR (one repo per PR) lands, then a hard failure for that repo.
6. **Settings are Amr's** — Pages enablement and any repo setting are changed only by Amr.

## 15. Evidence for major changes and frontend PRs

_(amendment `major-change-evidence`, numbered at merge — see the [amendment log](amendments/README.md); § 13 is `eval-baseline-risk-tiers` (0011), so the number § 15 is final; interim reviewer amended by `qa-lead-bridge`; extends § 7, § 12 and UPS-QA-50..53)_

1. **Major change: JEV decides** — JEV, the harness-level agent logic engine (docs/JEV.md), judges whether a PR is major. It weighs these heuristic inputs: public interface or user-visible behaviour, § 12.3 areas, indexed features, the size and spread of the diff, and dependencies or toolchains. There are no fixed thresholds. The `major` label overrides JEV. After § 13 is ratified, JEV must pass its own eval set. **Interim, until JEV exists:** the heuristics flag candidates, the completeness reviewer decides, and when in doubt a PR is treated as major.
2. **Test evidence** — a major PR lists the tests added or updated (or why none apply) and links the green CI run for its head commit.
3. **Frontend detection** — a PR impacts the frontend when it touches the default frontend globs (layouts, includes, styles, assets, pages, posts, HTML/CSS/component files, the console web app, `_config.yml`) or the repo's extra `verify/verify.yml` `frontend_paths:`.
4. **Visual evidence, every frontend PR** — before/after screenshots or a recording of each affected page at two or more viewports (`test/evidence/<slug>/` or the PR body); `skip-evidence` only with a reason when nothing renders differently.
5. **Completeness review by JEV and QA Lead** — every major or frontend PR is reviewed for completeness by JEV and the QA Lead bot, and both must pass. The author is never a reviewer: if one of the bots authored the PR, Amr reviews in its place. A bot reviewer cannot waive a requirement. **Interim (a short bridge):** building QA Lead is the priority (#492). Until QA Lead runs, the completeness review is warn-only, with Amr as the fallback reviewer. QA Lead takes over as soon as it exists, and JEV joins later.
6. **Fit with § 12** — the completeness review is a required review under § 12.1.2. It adds to the review gate and does not replace it, and only Amr merges amendments.
7. **Enforcement** — the PR template sections and a `tools/conformance.py` check, warn-only per repo until its fan-out PR lands, then a hard failure.

## 16. AI-ready foundation

_(amendment `ai-ready-foundation`, numbered at merge — see the [amendment log](amendments/README.md); follows § 15 `major-change-evidence`; extends § 7, § 14 and UPS-AGENT)_

1. **Common foundation** — every active repo is AI-ready: it exposes an API layer, an MCP layer, agent docs and machine-readable metadata, sized to its type.
2. **By repo type** — apps and services: REST with a committed OpenAPI 3.1 document, plus an MCP server. Content sites: a static JSON data API on the public site, schema.org JSON-LD and their own MCP server, shipped as a local stdio server in the repo. Tools: `--json` output on every command, plus an MCP server or `server.json`. Libraries, themes and kits: agent docs and metadata only.
3. **Agent docs** — `AGENTS.md` per UPS-AGENT and `llms.txt` on the public site (§ 14).
4. **Metadata** — an `ai-ready.yml` manifest naming the repo's type and layers; MCP manifests follow the MCP Registry `server.json` schema; a repo that runs an agent publishes an A2A Agent Card at `/.well-known/agent-card.json`.
5. **Shared kit** — repos start from the hub's `templates/ai-ready/` kit, fanned out and stamped like the other kits.
6. **AIEO validates** — the AIEO engine in the hub's `tools/aieo/` scores AI-readiness, run by `tools/conformance.py` as check `ai-ready`: warn-only per repo until its fan-out PR lands, then a hard failure.
7. **Held to § 13** — until AIEO passes its own eval set, only the structural checks can fail a build and the score is advisory; after that, a score below the minimum (80/100) also fails.
8. **Exemptions** — archived and retired repos are exempt; a layer may be marked not applicable with a reason the § 15 completeness review accepts.
9. **No secrets** — no layer exposes secrets or private data; private repos expose their layers to the fleet only, at $0 Actions spend.

## 17. Centrally managed loop switches

_(amendment `central-loop-switches`, numbered at merge — see the [amendment log](amendments/README.md); follows § 16 `ai-ready-foundation`; extends § 7 and § 10; feature `central-loop-switches`, requirement `FR-NEW:central-loop-switches`, bamr87/bamr87#526)_

1. **Every loop has a switch** — every scheduled or AI-calling workflow in the hub, `templates/` and the fleet checks a kill switch before doing work.
2. **One source of truth** — switch state lives in `_data/fleet.yml` `switches:` (global, group, loop and repo levels, each with state, reason, who, when and optional expiry); the most restrictive level wins, and repo variables are projections of it.
3. **Dry-run first** — tools that apply switch state show the diff by default and change live variables only with explicit apply and confirm, scoped to a repo, a loop, a group or everything.
4. **Audit** — every flip records who, what, scope, reason and old and new state in the fleet activity log.
5. **Drift** — the drift check reports mismatches between the map and live variables, and expired entries.
6. **Conformance** — the workflow atlas fails a scheduled or AI workflow without a switch; warn-only per repo until its fan-out PR lands, then a hard failure.
7. **Exemptions** — workflows with no schedule and no AI call, and archived or retired repos, are exempt; any other exemption needs a reason the § 15 completeness review accepts.
8. **No secrets** — no switch tool reads, prints or changes a secret.
