# Harness Console

The local control plane's **front end**: one service that lets you view, manage, orchestrate, and deploy the fleet's AI harnesses from a browser, using exactly the `tools/` entrypoints the CLI and CI run. The same page, built static, **is** the public site on GitHub Pages — https://bamr87.github.io/bamr87/ — where it reads a snapshot of this API instead of the API itself, and where a visitor can connect GitHub or a running console to get the write path back ([docs/CONSOLE-PAGES.md](../../docs/CONSOLE-PAGES.md); [docs/HARNESS-OPS.md](../../docs/HARNESS-OPS.md), "The two planes").

## Run it

```bash
tools/dash console              # native: bootstraps .venv-console (latest deps), serves http://127.0.0.1:4001
tools/dash console --docker     # the compose service (same devenv image, loopback port 4001)
docker compose up -d console    # same thing
CONSOLE_RELOAD=1 tools/dash console   # auto-reload while editing app.py / core.py
cd tools/console/web && npm run dev   # the page with hot reload on :5173, proxied to a running console
```

For the dev server's Terminal page, start the console with `DASH_CONSOLE_ALLOWED_ORIGINS=http://localhost:5173`, so the WebSocket admits that origin.

The console is the **runtime** of the local control plane, and this page is one of its two front ends. AI agents are a third, through the `fleet` MCP server ([`mcp_layer/`](docs/mcp-layer.md), which absorbed `tools/fleetcore/mcp_server.py`), whose action tools go through this same job API and confirm gate. The terminal dash (`tools/dash tui`, `tools/tui/`) is the other human one: it reads the same views from [`tools/fleetcore/`](../fleetcore/README.md), binds the same keys (keys v1) in the same bashOS palette, and submits jobs to this process's API, so a job started in either one shows up in both. The page also runs the terminal dash itself, on its Terminal page. Under Docker the TUI reaches it over a Unix socket (`CONSOLE_UDS`, `serve.py`) in a volume only the `tui` service mounts, which keeps the DNS-rebinding allowlist loopback-only.

The console is one of the local stack's three services; `docker compose up -d phoenix` starts the trace store it links to (http://127.0.0.1:6006), and `tools/dash lake sync` fills the data lake the Traces page reads (see [docs/HARNESS-OPS.md](../../docs/HARNESS-OPS.md), "The local stack").

Credentials are inherited from the process environment (`gh auth login`, or `GH_TOKEN` / `FLEET_TOKEN` / the Claude tokens in `.env` for the compose service) — and, since 0.3, they can also be handed to the console **on the Credentials page** when it starts without them: a pasted value lives in this process's environment (which is exactly what a job inherits) and dies with the process, a GitHub token can instead go to `gh auth login --with-token` over stdin so the CLI's own store keeps it, and writing anything to the gitignored `.env` (mode 600) is a separate, explicitly confirmed step. Values are never returned, logged, or placed on a command line; every status document reports credential **names**, presence and provenance only. `DASH_CONSOLE_AUTH=off` refuses every credential write; set `DASH_CONSOLE_TOKEN` to require `Authorization: Bearer …` on the API when the console is reachable beyond localhost. Independently of that, the console answers only to loopback `Host` values: binding to 127.0.0.1 does not by itself stop a hostile page from resolving its own hostname to 127.0.0.1 (DNS rebinding) and then talking to this origin as same-origin, which on a console that can dispatch workflows and run `--apply` fan-outs is a real lever. Front it with another hostname by naming that hostname in `DASH_CONSOLE_ALLOWED_HOSTS` (comma-separated) — and set the token as well.

## The page

A React + TypeScript app on **Mantine** (app shell, Spotlight palette, modals, notifications), **TanStack Query** (one cache for every API document) and **React Router** (every view is a URL), built with Vite from [`web/`](web/README.md) into `web/dist/`, which `app.py` serves. `run.sh` rebuilds it whenever a source file is newer than the last build, at latest versions and without a lockfile, like the venv. Without `npm` the API still serves, and `/` says how to build the page.

Nine sections, each a group of pages, with a drill-down for every entity. Every repo name, operation, job, loop, site and config block is a link to its own page.

**The frame.** The sidebar's sections fold: the one holding the current page opens itself and stays in view, the rest stay as you left them (this browser remembers), and a number beside a page says what needs attention there (Overview, Inbox, Health, Jobs), summed on a folded section. The palette opens on the pages this browser last visited. A page that throws is contained with the header and sidebar still up, a failed load offers **Try again**, a failed refresh keeps the last answer on screen under a warning, and when the console stops answering one banner says so and clears by itself. Below the `md` breakpoint the header's status chips sit at the foot of the sidebar. Enter belongs to the focused control and opens the selected row only when nothing has focus; sortable headers are buttons, every row that opens a page carries a real link, the first Tab reaches a skip link, and motion stops under `prefers-reduced-motion`.

Running an operation works the same from any button, form or palette pick. A GitHub-writing operation says in plain words what it will do and asks first (the server refuses a write without `confirm=true` anyway). The job then opens in a side drawer on its live log, so the page you were on stays put. A job that succeeds refreshes every document, because its output is new data in the working tree.

**Jobs keep their history.** The index (`jobs.json`) and every job's log live in `DASH_CONSOLE_JOBS` — under Docker the `console-run` volume, so a restart or a recreated container keeps them; a job that was running when the process died comes back `interrupted`. Jobs past the newest 200 are dropped with their logs, and **Clear finished** / **Clear failed** on the Jobs page (`DELETE /api/jobs?status=…`) forget finished jobs and delete their logs — never a running one. The page groups the list two ways: every run, newest first, filtered by status, operation group and text; or **By operation**, one row per operation with its latest result, run count and success rate. Three guards stop jobs that cannot succeed: the **lake writers** (`lake-sync`, `lake-sessions`, `lake-export`, `observe-ship`, `content-sync` — `exclusive="lake"`) run one at a time, a second answering 409 with the job that holds the lake rather than dying on `database is locked`; **Docker-backed** operations (`observe-up`/`down`/`reset`) report themselves unavailable when this process has no `docker compose` and daemon — the case in the console's own container, which is never given the socket — with the host command to run instead; and `loop-run` (below) reports itself unavailable when no `claude` CLI is on this process's PATH — the console container and the devenv image have none — and holds a key per loop (`loop:<loop>`), so two local runs of one loop never interleave while different loops may run side by side.

**A loop's agent step, run here (`loop-run`; P2 of epic #484, [docs/JEV.md](../../docs/JEV.md#the-loop-runner-p1)).** Every loop page shows the agent steps the JEV loop runner can run on this machine (each `tools/jev/steps/<loop>/<step>.yml` with a `local:` block, read through `tools.jev` itself) and offers **Run locally** beside **Dispatch in CI** (`L` on the page; the TUI's `L` runs the selected repo). The op is `tools/dash loop run <loop> [step] --target <name> --json`: the same spec, planner and prompt bytes CI renders, one capped attempt per item inside the § 13.8 sandbox, then the dry-run preview under `.fleet/runs/<run_id>/` — nothing is filed. `rehearse` stops before the model call at $0 and needs no confirm; a live attempt spends Claude budget (API-equivalent, an estimate; held to `budget.loops`), so the confirm gate asks first and one confirmed job runs at a time. `apply` files the reviewed preview through the engine's own publish gate — the OPS remote-write path, constitution § 11.8 (amendment `ops-remote-write-path`, option (a) of #487): a GitHub write at tier high, refused without the confirm, the publish token probed with `gh api user` before anything is written, held to the reviewed bytes, never with `--scheduled` (the op never passes it) and never with `rehearse`; `run_id` publishes an earlier run's reviewed preview (`tools/dash loop publish <run_id> [--item <key>] --apply`), `item` naming the preview by its key — `owner/repo`, or `owner/repo:path` for the doctor's per-workflow items; never a registry name, which matches no preview — when the run has several, and without `apply` that call is the read-only "matches / differs" check. A step whose filer cannot file yet (`can_apply` false in the op's `agent_steps`: evolve and the agent fill until bamr87/bamr87#488's publish step lands) refuses `apply` before anything runs, in the op and in the engine alike, so no attempt is ever paid for a filing that could not happen. The MCP's `console_run` reaches the same op with `confirm=true`, so the gate is this console's. The engine's run record (`--json`) is parsed once, in [`tools/fleetcore/loopjob.py`](../fleetcore/loopjob.py), into the fields the job page and the TUI render — status, spend with its label, model, turns, one row per item — and `JEV_WORK_ROOT` / `JEV_RUNS_DIR` pass through from the console's environment unchanged (they must point outside the hub and outside Claude's temp root, which the engine refuses). Test files point `DASH_CONSOLE_JOBS` at a temp dir before importing the console, because importing `app` builds a job manager on whatever directory that names.

**The header's tree chip** counts the hub's own uncommitted files: `git status --ignore-submodules=dirty`, so edits inside a submodule's working tree (which the hub cannot commit) stay out of it while a moved submodule pointer still counts. A plain `git status` walks all ~40 submodules and took 17 seconds over the Docker Desktop bind mount, past `run_quiet`'s timeout, so the chip used to read "clean tree" while every poll stacked another walk. Concurrent `/api/state` polls now share one answer for ten seconds, a status that fails or times out reads "tree unknown", never "clean", and a timeout kills the command's whole process group. Under Docker the service runs with `init: true`: `serve.py` is PID 1 and never reaps processes it did not start, so orphaned children and timed-out healthcheck `curl`s used to pile up as zombies (the stacked git walks pinned a CPU and were what timed the healthcheck out).

### Refine — the harness itself, and the review queue

**Harnesses → Refine** (`/refine`, `/api/refine`; [docs/HARNESS-REFINEMENT.md](../../docs/HARNESS-REFINEMENT.md), ADR 0004 P2) is JEV capability three in the page, every part of it $0: **Surface** runs the harness-surface check over the hub (the context-file chain against its cap, every skill's frontmatter, the subagents, the hooks block's shape, every script a component names, the MCP file) and the sweep over every checked-out fleet repository, one row each with its problems; **Plans** shows one Propose–Probe–Compose plan per agent step (R = 4k rollouts, P = 3k sessions, the ceiling from the step's own `budget.call_sites` cap and `harness_refinement.stage_usd`, judged against this month's `budget.loops`, the tunable files a candidate may edit, the hard rules it may not, the domain's library) with the schedule unfolded on demand; **Review queue** lists every local loop-run attempt whose dry-run preview has not been filed — the preview and each body readable in place, **Check it still matches** (`loop-run` with `run_id` + `item`, $0) and **Approve and file** (`run_id` + `item` + `apply`: the engine's publish gate, constitution § 11.8, behind the confirm) beside it, disabled where the step's filer cannot file yet (#488); **Evidence** lists the trees `refine-evidence` built under `.fleet/refine/` and opens any file of one, redacted as the proposer would read it; **Library** is the experience library (`_data/harness_library`), its uncommitted entries flagged, with the $0 reflector's form (**Record a lesson** → `POST /api/refine/library`, validated and leak-checked by `tools.jev.library`, written to the working tree, never committed). The ops are `refine-surface`, `refine-plan`, `refine-evidence` and `refine-library-check` (group *refine*, `tools/dash refine …`); each loop page with a local agent step lists `refine-plan` in its local half. The public build publishes the surface, the sweep, the plans (without the ledger position) and the library; the evidence trees and the review queue exist only on a console.

### The assistant

**Operate → Assist** (`/assist`, `/api/assist`, the `assist` op) answers a question about the fleet from the fleet's own data: one headless Claude Code session (`tools/dash-gen ai-run`, the prompt in [`assist.prompt.txt`](assist.prompt.txt) with the question and the page it was asked from filled in) whose only MCP server is this console's own layer over stdio (`--strict-mcp-config`, pointed at `DASH_CONSOLE_URL`, the token inherited from the process environment, never a file or an argv), whose tools are `mcp__fleet`, `Read`, `Grep` and `Glob` on the hub checkout and whose denied list names every writing tool and the network, under `--permission-mode dontAsk`, `--setting-sources user` (the hub's own hooks stay out of it), the model, turn cap and dollar cap of `_data/fleet.yml` `assistant:` (the model an exact id, § 13.3), a wall clock, and `--usage-limit skip`. It spends, so it is confirm-gated like a live loop attempt (`confirm: spend`), runs one at a time (`exclusive: assist`), says why it cannot run where there is no `claude` CLI or where `assistant.enabled` is false, and every answer is a job: the question, the answer (rendered as Markdown through the site's sanitizer), the turns, the models and the cost (API-equivalent (estimate), from the result and outcome files ai-run wrote) are the job's `assist` view, on the Assist page's thread and on the job's page above the raw log, and the AI ledger holds its row like every other local run. It cannot start a job, file anything, edit a file or reach the network; when an action is the answer, it names the operation or page and the person runs it. The HARNESS.md roadmap's "assistant in the console frontend" is this, in its read-only form; a remote assistant (Grok Bot over the MCP HTTP transport) reaches the same tools.

### GitHub, through the console's OAuth App

The **GitHub** page connects the console to GitHub through an [OAuth App](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps) you register once (`github_link.py`):

1. Create the app at github.com/settings/applications/new. Set the callback URL to `http://127.0.0.1/api/github/oauth/callback` (GitHub accepts a loopback callback on any port), and tick **Enable Device Flow**.
2. Give the console its client ID, and optionally its secret, as `GITHUB_OAUTH_CLIENT_ID` and `GITHUB_OAUTH_CLIENT_SECRET`. Paste them on the GitHub page, set them on the Credentials page, or put them in `.env` (compose passes both through).
3. Press **Connect**.

| Flow | Needs | How it goes |
| --- | --- | --- |
| **Device code** (default) | the client ID | GitHub shows a short code; you type it at github.com/login/device and the console polls for the token, at most once per GitHub's interval. Works natively, in Docker and over SSH |
| **Browser redirect** | ID + secret | GitHub's authorize page, back to `/api/github/oauth/callback`. A single-use `state` minted by an authenticated request, plus PKCE (S256), protects the return. The callback cannot carry the console's bearer token, so the state is its guard |

The token never reaches the page. It goes where you chose: **this console session** (`GH_TOKEN`, inherited by every job, gone when the console stops), **the gh CLI's login** (`gh auth login --with-token` over stdin), or **the session plus `.env`** (explicit confirm). The console then acts as that account. It resolves its identity the way `gh` does (`GH_TOKEN`, then `GITHUB_TOKEN`, then gh's stored login), so the page, the jobs and the terminal dash agree. **Disconnect** clears the session token and, when the secret is known, revokes it at GitHub.

Repo management reads every repo the account can see, and **writes only to fleet repos the hub owns**: the registry's repos under the hub's owner, plus `hub.repo` and `hub.shared`. An external mirror such as `microsoft/skills` stays read-only. The writes are:

- **Issues:** open, comment, close (completed or not planned), reopen, add and remove labels.
- **Pull requests:** comment and label. The console never merges.
- **Runs:** re-run failed jobs, cancel.
- **Workflows:** enable and disable.

Each write states what it will do and asks first, and the server refuses one without `confirm=true`. Each is recorded in the action log on the GitHub page. Nothing merges, deletes, pushes or changes repo settings. `DASH_CONSOLE_GITHUB_WRITES=off` makes the surface read-only, and `DASH_CONSOLE_AUTH=off` also refuses connecting.

### The app portal

**Fleet → Apps** (`/apps`, [docs/FRONTEND-PLATFORM.md](../../docs/FRONTEND-PLATFORM.md#the-app-portal), [ADR 0005](../../docs/adr/0005-console-as-fleet-portal.md)) lists every frontend the registry declares and opens one inside the console at `/apps/:id`: the **Live** site or the **Local** dev stack on this machine, at the page's width or at one of the verify kit's device sizes, with a path box to move inside the app. `GET /api/apps` is `fleetcore.apps.apps_view()`: each `frontend:` block joined to its `entry_url` and to the ports its compose-hosted stack publishes in `_data/ports.yml`. It is the document `tools/dash apps` prints, and it carries addresses only.

Whether an address answers is asked by the browser, because a frame loads from where the reader sits and not from this process: a stopped local stack shows the command that starts it (`tools/dash dev up <project>`), never an error page in a frame. The list checks every address only when a console is connected. The public build lists addresses, asks nothing on load, and checks a local stack only after the reader clicks, since a public page must not reach into a visitor's machine unasked.

A frame points only at a registry address plus a path inside it: the query string picks among an app's targets and never supplies a URL, and a path that would leave the app's own base address is dropped. Frames are sandboxed without top-navigation, so an app cannot take the console's tab. An app served from the page's own origin (the public build beside `bamr87.github.io/<repo>/`) is framed without `allow-same-origin`, so it cannot read what the page stores; such an app starts without its saved preferences and one that needs browser storage may not render there. The console's Content-Security-Policy names exactly the launcher's origins in `frame-src` and `connect-src` (`fleetcore.apps.target_origins`, held equal by `test_console.py`), so a new origin is a registry change. `tools/dash apps check` reports from a terminal whether each address answers, whether it moves to another origin and whether it may be framed.

### The desktop: bashOS as the OS shell

**Fleet → Desktop** (`/desktop`, [docs/FRONTEND-PLATFORM.md](../../docs/FRONTEND-PLATFORM.md#the-os-shell-bashos), [ADR 0005](../../docs/adr/0005-console-as-fleet-portal.md)) is the bashOS desktop in the browser: dotted paper, an icon for every fleet app, floating windows, a taskbar with a bashOS button. It is its own chrome, outside the console's sidebar. Three layers: the **OS shell** (the desktop and its windows), the **App Shell** every window shares (the Apps page's controls: where the app runs, a device size, a path, reload, open outside), and the **app** (a fleet frontend, framed under exactly the Apps page's rules).

The window state is bashOS's own layout reducer, `web/src/vendor/bashos/shell.js`, byte-identical to the one `bashos gui` runs (`test_bashos_shell.py` pins it): open, focus, move, resize, snap to an edge, minimize and restore, tile and cascade, at most eight windows. The icons are a dock beside the window area, so a maximized or tiled window never covers the launcher. Shift-click an icon for a second window of the same app (Live beside Local). `⌘\` cycles windows. The taskbar's link button copies a `?windows=` address that reopens the desktop; a layout carries scene and app ids and geometry, never an address, and ids the registry does not declare are dropped. The tab's last layout comes back on reload. Below 900 px the desktop is a home screen: the icons, then one app at a time.

**The console's own pages open as windows.** The taskbar's **bashOS** button lists every page; the **Console** icon opens Overview; and with the Desktop on screen a pick in the palette opens a window instead of leaving. A page in a window is a frame of this same app: found framed (`EMBEDDED`, `web/src/api/backend.ts`), the page drops its header and sidebar, which is the reducer's `plain` experience, and tells the desktop its route, so the window is titled after the page it is on and a shared or restored layout reopens it there. For that the console's policy is `frame-ancestors 'self'`: it may be framed by its own origin and by no other, a framed fleet app included (`test_console.py`). A window holds only a path whose first segment is a page in the navigation, never the Desktop itself, and a route message is heard only from this origin, from a frame in one of the desktop's windows. On a phone there is no taskbar, so the Console icon leaves for the classic console.

The **Fleet** icon opens every repo in the registry, grouped by the frontend component it has or is owed (`doc.repos` in `/api/apps`, `tools/dash apps plan`). A repo with no frontend opens a window that says which component it gets next; that window is the placeholder the generated repo app replaces. The colours are the bashOS GUI's paper palette, `--os-*` in `/theme.css` (`fleetcore.theme.OS_TOKENS`); inside a window the console's own roles apply.

### The generated repo app

Every repo in the registry is an app, including the ones with no interface of their own (ADR 0005, phase F1). `/apps/<id>` frames a repo's frontend when the launcher can; otherwise it renders `RepoApp`, and so does a repo window on the Desktop: an **Overview** (description, stack, licence, health, CI, last commit, open work, the standards audit from `_data/conformance.yml`, automation, and how to get it), the **README**, **Open work** and **Automation**. A repo that is owed a different component (an editor extension's preview, a terminal UI, a frontend with no address) opens the same way and says which.

`GET /api/project/<name>/readme` reads the README from the repo's submodule checkout on this machine: the path is the registry's `submodule_path` and must sit directly under `projects/`, a symlink is not followed, and a file over 200,000 characters is cut and says so. In the page its relative links point at the file's neighbours on GitHub and its images become links, because the console loads images from its own origin only. The public snapshot never calls the route and publishes no README: some fleet repos are private, and one checked out on the build machine must not reach the public site.

### Starting a local stack

A stopped Local target offers **Start the stack** in the App Shell, on the Apps page and in a Desktop window; a running one offers **Logs** and **Stop the stack**. They are the operations `dev-up`, `dev-down` and `dev-logs`: each takes one compose-hosted project from `_data/ports.yml`, never the hub (`dash dev up hub` would start a second core) and never `--all`. A start or stop holds that project's slot, and different projects run side by side. `dev-logs` prints the last 200 lines and ends, because a job with no end has no time limit; to follow live, run `tools/dash dev logs <project>` in a terminal. After a start the page asks the address every three seconds for 90 seconds and frames the app when it answers. Nothing starts on page load.

These need Docker, so they run from a native console (`tools/dash console`). The core console's container has no socket on purpose, and there the page says so and shows the terminal command.

### The Work board

**Harnesses → Work board** (`/work`, [docs/WORK-BOARD.md](../../docs/WORK-BOARD.md)) puts every open item in the fleet on six lanes (triage, ready, in flight, review, blocked, on hold), in the order the loops will take them, and marks what each loop's next run takes. Dragging stages a plan: within a lane it pins the order, across lanes it moves an issue (its `agent:` labels) or a roadmap spec (its `status:`), and across the P0–P3 columns it reprioritises. `POST /api/work/preview` redraws the board as the plan would leave it, cut lines and throughput included. **Apply** (`POST /api/work/apply`) asks once, then moves the labels through the same GitHub write path as the GitHub page (`issue.labels`: fleet-scoped, confirm-gated, logged). It writes `_data/work_queue.yml` and the `roadmap.yml` lines in the working tree, returns the diff, and commits nothing. A PR, a spec package and a `BACKLOG.md` item can be pinned and reprioritised but not moved, because their state belongs to the PR, `spec.md` and the append-only backlog. Spec packages and backlog items are read from submodule checkouts, so the public snapshot's board is read-only and has neither.

### Per-project health on startup

`_data/project_health.yml` is gitignored and only `dash-gen health` writes it, so a fresh clone used to show blank health and red/amber/green 0/0/0. On startup the console checks it (with `_data/project_health_meta.yml`) and, when it is missing, undated, or older than `harness.trip_wires.stale_data_days`, starts the allowlisted **health** operation as an ordinary job. The job shows on the Jobs page and runs in the background. It is cancelled after `CONSOLE_AUTO_HEALTH_TIMEOUT` seconds (default 300). It needs a GitHub token like the manual operation does; without one it fails and the page stays as before. `CONSOLE_AUTO_HEALTH=0` turns it off.

### The terminal dash, inside the page

**Operate → Terminal** runs the real terminal dash (`tools/tui/app.py`, Textual), not a re-implementation. `tui_bridge.py` starts it on a pseudo-terminal and relays it over the `/api/tui` WebSocket, and xterm.js draws it in the TUI's own bashOS dark palette (`/api/theme`). It joins this process's runtime (`DASH_CONSOLE_URL` points back here), so a job its `:` palette starts appears on the Jobs page, behind the same allowlist and confirm gate. Its `o` / `l` keys open links in a new tab of *this* browser through a private OSC sequence, rather than on the machine running the console. At most `CONSOLE_TUI_MAX` (default 4) sessions run at once, and closing the page hangs up the session's whole process group.

No HTTP middleware sees a WebSocket handshake, and CORS does not apply to one, so the bridge makes its own checks before any process exists:

- the **Host** allowlist, repeated from the HTTP guard;
- the **Origin** must be this console's own page, which stops cross-site WebSocket hijacking (add a dev origin with `DASH_CONSOLE_ALLOWED_ORIGINS`);
- when `DASH_CONSOLE_TOKEN` is set, the first frame must carry it, because a browser cannot put a bearer token on a WebSocket.

## tools/dash ops

`tools/dash ops` ([`ops_cli.py`](ops_cli.py)) runs the operation allowlist from a terminal, and the Claude Code slash commands (`/harness:*`, `/loops:*`, `/console:*`, [`.claude/README.md`](../../.claude/README.md#slash-commands-the-harness-and-its-loops-one-stage-at-a-time)) run every stage through it. It is a surface, never a code path: the operations, their validation and the confirm gate are `core.py`'s.

```bash
tools/dash ops list [--group G]          # every operation, by group, with its gates
tools/dash ops show conflicts-resolve    # what it runs, its parameters, why it may be unavailable here
tools/dash ops run loop-run loop=repo-scout target=kvlite rehearse=true
tools/dash ops run dispatch workflow=repo-scout fields.dry_run=true --explain   # argv and gate; runs nothing
tools/dash ops run dispatch workflow=repo-scout fields.dry_run=true --confirm   # a GitHub write: asked first
tools/dash ops loops                     # the loops table, each loop's operations and slash command
tools/dash ops jobs [<job-id>]           # the running console's jobs, or follow one
```

A run goes to the running console when it answers at `DASH_CONSOLE_URL`, serves this checkout (`/api/health`'s `repo_root`) and can run the operation itself; the job then shows on the Jobs page and in the terminal dash, and the console's locks apply. Otherwise it runs here in the foreground with the same argv, and refuses when a console job already holds the lock it needs. `--here` and `--console` force either. A gated call without `--confirm` exits 3 and prints what it would run; the other exits are in the module's docstring.

The operations the loop commands needed and the console lacked are in `OPS` too, on the loops' cards: `agents` (the agent inventory's check), `pm` (the PM review's views), `conflicts` (JEV's scan, triage and budget, read-only) and `conflicts-resolve` (resolve one pull request or sweep them all; a GitHub write unless `dry_run`), and `evidence` (one issue's evidence bundle). The loops table gained `jev_conflicts` and `fleet_pm`, and both workflows are dispatchable.

## The decision queue

`GET /api/decisions` answers "what waits on Amr?" for the whole fleet in one call ([docs/DECISION-INDEX.md](../../docs/DECISION-INDEX.md)): `needs-amr` items, pull requests that change a constitution, an amendment or an ADR, failing or major Dependabot pull requests and ready-to-merge pull requests, each with its reason, plus a per-repo inventory. `decision_index.py` reads the fleet with three GraphQL searches and parallel merge-state batches under the console's own GitHub identity, keeps the result in `.fleet/decisions/index.json` (gitignored, owner-only) and serves it until `decisions.ttl_s` in `_data/fleet.yml`. Every answer returns inside a time budget (`budget`, default `decisions.budget_s`) and carries `status` — fresh, partial, stale, expired or unavailable — with `warnings`, `errors` and a `hint`, so a slow or unreachable GitHub yields a dated answer and never a hung request. The same document is `tools/dash decisions --json` and the MCP's `decision_queue`; the operations `decisions` and `decisions-refresh` print it as a job. It is read-only and is never part of the public snapshot, because the index can hold a private repo's titles. Tests: `python3 tools/console/test_decision_index.py` (an in-memory GitHub, no network).

## What it refuses to do

- Run anything outside the allowlist in `core.py` (`OPS`): parameters are validated by regex/range and become argv elements, never a shell string. A Config number field refuses `inf` and `nan` as well as a negative: a `.inf` ceiling would make every gate that holds spend inside it vacuous. The Terminal page runs exactly one program, the terminal dash, and that program submits its jobs through the same allowlist.
- Write to GitHub without an explicit confirm (`apply`, `dispatch`) — and only one such job runs at a time (constitution § 11.8, the OPS remote-write path). Spend Claude budget without one either: a live `loop-run` attempt asks first.
- File anything from a local loop run: `loop-run` takes `apply` only to refuse it (#487's § 11 decision is the maintainer's), and the preview it leaves under `.fleet/runs/` is filed from a terminal.
- Write to a repo the hub does not own, or merge, delete or push through its GitHub page. Its GitHub writes are issues, runs and workflows, each confirmed and logged.
- Be framed by another origin. `frame-ancestors 'self'` admits this console's own Desktop and nothing else: not another site, not a fleet app it frames.
- Frame or fetch an address the registry does not declare. The Apps page's frames and reachability checks go only to the launcher's origins, which the Content-Security-Policy lists one by one; there is no wildcard and no URL parameter.
- Publish a repo's README. The repo app reads it from a checkout on the operator's machine; the public snapshot carries none.
- Commit, push, or merge. Generated data lands in the working tree; you review it in git.
- Invent contract structure. The Config form edits declared keys only: a key `fleet.yml` does not already carry is shown read-only, and the policy keys the file itself calls non-negotiable (`rotation.hub_first`, `issue_pipeline.autonomy.never_merge`) are not offered at all.
- Hand a credential back. Values go in; names, presence and provenance come out. A token pasted for `gh` travels on stdin, and `.env` is written only on an explicit confirm — never if git tracks it.
- Publish the lake. `.dash-lake/` is gitignored (it holds run logs); traces go only to the Phoenix endpoint you configured, and `PHOENIX_API_KEY`, when set, is forwarded and never shown.
